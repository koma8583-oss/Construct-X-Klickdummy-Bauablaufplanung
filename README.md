# TaktKoord — Takt Coordination Flow

A proof-of-concept for federated Takt coordination in construction projects.

The Generalunternehmer (GU) or Generalplaner manages the complete Takt schedule and delegates individual Takte to Nachunternehmer (NU) for review. Each NU checks the request against their own local resource plan and responds with a confirmation, alternative time window, or rejection — without exposing internal resource data to the GU or to other parties.

The information exchange is currently implemented via REST APIs and standardised JSON messages, with a shared Hub acting as a message broker. The architecture is designed so the local transport layer can later be migrated to Tractus-X and an Eclipse Dataspace Connector (EDC), while domain processes and JSON contracts remain unchanged.

## Applications and components

| Directory                  | Role                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| `artifacts/ag-app`         | **GU-App (Auftraggeber)** — React/Vite SPA. GU users manage projects, Takt schedules, and delegations. Served at `/`. |
| `artifacts/an-app`         | **NU-App (Nachunternehmer)** — React/Vite SPA. NU users review incoming Takt requests, manage resources, and respond. Served at `/an/`. |
| `artifacts/hub-app`        | **Hub-App** — React/Vite SPA. Hub admins monitor coordination messages and organisation overview. Served at `/hub/`. |
| `artifacts/api-server`     | **API Server** — Express 5, port 8080. Serves all three frontends. JWT-based auth at `/auth-service/*`. |
| `lib/db`                   | **Database** — PostgreSQL via Drizzle ORM. Schema in `lib/db/src/schema/`. |
| `lib/api-spec`             | **OpenAPI specification** — `lib/api-spec/openapi.yaml`, OpenAPI 3.1. Single source of truth for all API contracts. |
| `lib/api-client-react`     | **Generated API client** — React Query hooks generated by Orval. Do not edit manually. |
| `lib/api-zod`              | **Generated Zod schemas** — Validation schemas generated by Orval. Do not edit manually. |

## PoC scope and limitations

This project does **not** use an Eclipse Dataspace Connector (EDC) or the Dataspace Protocol (DSP). The dataspace exchange is simulated through REST endpoints, standardised JSON messages, and a local Hub component. No digital identities, Verifiable Credentials, or policy negotiation are implemented in this PoC.

---

## Data sovereignty

| Party | What they hold                                        |
| ----- | ----------------------------------------------------- |
| GU    | Complete Takt schedule for their own projects         |
| NU    | Complete local resource plan and availability data    |
| Hub   | Coordination messages and transport metadata only     |

Additional rules:

- There is no shared central resource plan.
- Each NU's other projects and clients remain hidden from the GU and from other NUs.
- The GU receives only the Takt details they own; the NU receives only the details released for them.
- Internal NU data (employee names, resource IDs, internal costs, full conflict lists) must never appear in a response to the GU or in a Hub message.

---

## Later migration path

The local HTTP transport between the GU, NU, and Hub can be replaced by an EDC connector pair without changing the domain processes or JSON message contracts. The planned additions for a real dataspace are:

- Digital identities and Verifiable Credentials per organisation
- Dataspace Policy negotiation before data transfer
- EDC Contract Agreements replacing direct REST calls
- Tractus-X connector infrastructure

Domain logic, JSON schemas, and the OpenAPI spec are designed to survive this migration unchanged.

## Installation and commands

```bash
# Install dependencies
pnpm install

# Start API server (development)
pnpm --filter @workspace/api-server run dev

# Start a frontend (example: GU app)
pnpm --filter @workspace/ag-app run dev

# Regenerate API client and Zod schemas from OpenAPI spec
pnpm --filter @workspace/api-spec run codegen

# Push database schema changes (development only)
pnpm --filter @workspace/db run push

# Type-check all packages
pnpm run typecheck

# Build all packages
pnpm run build
```
