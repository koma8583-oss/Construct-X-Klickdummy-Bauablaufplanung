# TaktKoord — Takt Coordination Flow

A proof-of-concept for federated Takt coordination in construction projects.

The Generalunternehmer (GU) or Generalplaner manages the complete Takt schedule for
their own project. They define the individual Takte — work packages allocated by zone,
trade, and time window — and send coordination requests to selected Nachunternehmer (NU).
No NU receives the full plan; each sees only the single Takt that concerns them.

Each Nachunternehmer checks the incoming Takt request against their own local resource
plan — crew availability, equipment, qualifications. They respond with an acceptance,
a set of alternative time windows, or a rejection, and may attach a generic reason code.
Internal resource data such as employee names, resource identifiers, costs, or other
projects never leaves the NU's system.

The information exchange is currently implemented via REST APIs and standardised JSON
messages, with a shared Hub component acting as a message broker. The architecture is
explicitly designed so the local transport layer can later be replaced by an Eclipse
Dataspace Connector (EDC) and the Tractus-X Dataspace Protocol, while the domain
processes and JSON message contracts remain unchanged.

## PoC scope and limitations

This project does **not** use an Eclipse Dataspace Connector (EDC) or the Dataspace
Protocol (DSP). The dataspace exchange is simulated through REST endpoints, standardised
JSON messages, and a local Hub component.

The following dataspace capabilities are **not implemented** in this PoC:

- **No digital wallets** — organisations are identified by database IDs, not
  cryptographic identifiers or W3C DIDs.
- **No Verifiable Credentials** — membership, role, and consent claims are not
  signed or verifiable by third parties.
- **No EDC policies** — there is no access-control policy engine; endpoint
  authorisation is JWT-based only.
- **No contract negotiation** — Takt requests are sent directly; there is no
  offer/counter-offer/agreement lifecycle per the Dataspace Protocol.
- **No shared central resource plan** — each NU's full resource plan stays
  exclusively on the NU side and is never transferred in whole to the GU or the Hub.

## Data sovereignty

| Party | What they hold                                                              |
| ----- | --------------------------------------------------------------------------- |
| GU    | Complete Takt schedule for their own projects                               |
| NU    | Complete local resource plan and availability data                          |
| Hub   | Coordination messages and transport metadata only                           |

Additional rules:

- The GU receives **no** complete NU resource data — only the NU's decision,
  an optional generic reason code, and proposed time windows.
- The NU receives **no** complete GU Takt plan — only the single Takt snapshot
  that the GU explicitly released for this request.
- Other projects and clients of the NU remain hidden from the GU and from all
  other parties at all times.
- Internal NU data (employee names, resource IDs, internal costs, full conflict
  lists) must never appear in a response message or Hub payload.

## Later migration path

The local HTTP transport between GU, NU, and Hub can be replaced by an EDC connector
pair without changing the domain processes or JSON message contracts:

- **Local transport → EDC**: REST calls between components are replaced by
  EDC data transfers using the Dataspace Protocol; the application code above the
  transport boundary remains unchanged.
- **Domain processes preserved**: the five-step coordination flow (notification,
  detail retrieval, response, decision, update) is retained as-is.
- **JSON contracts reused**: the `TaktRequestNotificationMessage` and
  `TaktResponseMessage` schemas defined in the OpenAPI spec are designed to
  serve directly as the EDC transfer payload.
- **Digital identities, policies, and contract negotiation added later**:
  Verifiable Credentials, EDC Policies, and Contract Agreements are layered on
  top without requiring changes to the business logic.
- **Domain logic and transport logic must stay separate**: any code that
  encodes business rules (state machines, validation, repository functions) must
  not contain transport-specific logic, so the swap can be performed incrementally.

## Installation and commands

```bash
# Install dependencies
pnpm install

# Start API server (development)
pnpm --filter @workspace/api-server run dev

# Start a frontend (example: GU app)
pnpm --filter @workspace/ag-app run dev

# Regenerate API client and Zod schemas from OpenAPI spec
pnpm --filter @workspace/api-spec run codegen

# Push database schema changes (development only)
pnpm --filter @workspace/db run push

# Type-check all packages
pnpm run typecheck

# Build all packages
pnpm run build

# Run unit tests (api-server)
pnpm --filter @workspace/api-server run test

# Seed example TaktRequest data
pnpm --filter @workspace/scripts run seed-takt-data
```
