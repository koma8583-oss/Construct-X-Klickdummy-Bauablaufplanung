# Gesamtauftrag – Fehlerbehebung und Vervollständigung des PoC Task Coordination Flow

Arbeite den aktuellen Stand des Repositorys `Task-Coordination-Flow` vollständig durch und behebe die nachfolgend beschriebenen Sicherheitsprobleme, fachlichen Inkonsistenzen und fehlenden Bestandteile.

Führe nicht nur eine Analyse durch, sondern implementiere die Korrekturen vollständig.

## Ziel

Nach Abschluss muss der PoC folgende Eigenschaften besitzen:

* sichere Trennung der Organisationen
* AG sieht ausschließlich eigene Projekte
* jedes AG-Projekt besitzt eigene projektbezogene AN-Zuordnungen
* AN sieht ausschließlich eigene lokale Projekte, Ressourcen und Buchungen
* unveränderliche TaktRequest-Snapshots
* eindeutiger TaktRequest- und Response-Prozess
* konsistente Statusübergänge
* transaktional sichere Fachlogik
* idempotenter Nachrichtentransport
* funktionierende Fristen und Reminder
* vollständige AG-, AN- und Hub-Oberflächen
* Reporting und Audit entsprechend Aufgabe 8
* Schema-Version `1.0`
* erfolgreiche Tests, Typecheck und Builds

## Begriffe

Behalte die vorhandenen Begriffe des Repositorys bei:

```text
AG = Generalunternehmer beziehungsweise GU
AN = Nachunternehmer beziehungsweise NU
```

Führe keine globale Umbenennung durch.

## Nicht implementieren

Nicht Bestandteil dieses Auftrags:

* kein EDC
* kein Tractus-X Connector
* kein Dataspace Protocol
* keine Wallet
* keine Verifiable Credentials
* keine Policy Negotiation
* keine externe Schema-Registry
* keine produktive E-Mail- oder SMS-Integration

# Phase 1 – Sicherheitskritische Mandantentrennung korrigieren

## 1.1 Legacy-Projektendpunkte absichern

Prüfe insbesondere:

```text
artifacts/api-server/src/routes/projects.ts
```

und alle weiteren Projekt-Routen.

Folgende Endpunkte müssen zwingend die Organisation des angemeldeten AG prüfen:

```http
GET    /projects/:projectId
PATCH  /projects/:projectId
DELETE /projects/:projectId

GET    /projects/:projectId/contractors
POST   /projects/:projectId/contractors
DELETE /projects/:projectId/contractors/:anOrgId
```

## Verbindliche Regel

Ein Projektzugriff ist nur zulässig, wenn:

```text
authenticatedUser.orgType = AG
AND
project.agOrgId = authenticatedUser.orgId
```

Die Prüfung muss serverseitig erfolgen.

Die bloße Kenntnis einer `projectId` darf niemals genügen.

## Erwartetes Verhalten

* eigener AG und eigenes Projekt → Zugriff erlaubt
* anderer AG → `403` oder etabliertes sicheres `404`
* AN → `403`
* Hub → `403`
* nicht authentifiziert → `401`

## Keine ungefilterten Projektabfragen

Vermeide:

```ts
where(eq(projects.id, projectId))
```

wenn keine zusätzliche AG-Organisationsprüfung erfolgt.

Verwende sinngemäß:

```ts
where(
  and(
    eq(projects.id, projectId),
    eq(projects.agOrgId, authenticatedUser.orgId)
  )
)
```

## 1.2 Physisches Löschen entfernen

Historisch verwendete Projekte und AN-Zuordnungen dürfen nicht physisch gelöscht werden.

Ersetze physische DELETE-Operationen durch Statusänderungen.

Für Projekte beispielsweise:

```text
ACTIVE
COMPLETED
CANCELLED
ARCHIVED
```

Für Projekt-AN-Zuordnungen beispielsweise:

```text
PLANNED
ACTIVE
INACTIVE
COMPLETED
CANCELLED
```

Alte TaktRequests müssen weiterhin auf die damaligen Projekt- und AN-Zuordnungen verweisen können.

Falls DELETE-Endpunkte aus Kompatibilitätsgründen bestehen bleiben müssen:

* intern nur deaktivieren
* keine Daten physisch löschen
* Response und OpenAPI entsprechend dokumentieren

## Tests

Ergänze mindestens:

* AG A kann Projekt von AG A lesen
* AG A kann Projekt von AG B nicht lesen
* AG A kann Projekt von AG B nicht bearbeiten
* AG A kann Projekt von AG B nicht löschen oder archivieren
* AG A kann AN-Zuordnungen von AG B nicht lesen
* AG A kann AN-Zuordnungen von AG B nicht verändern
* AN erhält keinen Zugriff auf AG-Verwaltungsendpunkte
* deaktivierte Zuordnung bleibt historisch lesbar

# Phase 3 – Revisionsversand und Zustellstatus korrigieren

Prüfe insbesondere:

```text
artifacts/api-server/src/services/revision-service.ts
artifacts/api-server/src/lib/transport/local-hub-transport.ts
```

## Problem

Das Ergebnis von:

```ts
transport.send(...)
```

darf nicht ignoriert werden.

Der neue Revisionsrequest darf nur dann auf `DELIVERED` gesetzt werden, wenn das Transportergebnis tatsächlich:

```text
DELIVERED
```

ist.

## Umsetzung

Sinngemäß:

```ts
const transportResult = await transport.send(envelope);

switch (transportResult.status) {
  case "DELIVERED":
    // fachlichen Requeststatus entsprechend aktualisieren
    break;

  case "SENT":
    // nur SENT setzen
    break;

  case "FAILED":
    // Fachobjekte bleiben gespeichert
    // Request nicht als DELIVERED markieren
    // Outbox bleibt FAILED
    break;

  default:
    // keinen positiven Zustellstatus annehmen
}
```

## Verbindliche Regeln

* Transportfehler erzeugt keine zweite Revision.
* Transportfehler erzeugt keine zweite Taktversion.
* Transportfehler erzeugt keinen zweiten Snapshot.
* Retry verwendet dieselbe `messageId`.
* Fachliche Revision bleibt gespeichert.
* Technischer Status bleibt getrennt vom fachlichen Requeststatus.
* `DELIVERED` darf niemals angenommen werden, wenn kein positiver Transportnachweis vorliegt.

## Tests

* erfolgreiche Zustellung → `DELIVERED`
* Transport liefert `FAILED` → Request nicht `DELIVERED`
* Transport wirft Fehler → Fachobjekte bleiben erhalten
* Retry verwendet dieselbe Nachricht
* Retry erzeugt keine zweite Version
* Retry erzeugt keinen zweiten Request
* Retry erzeugt keinen zweiten Snapshot

# Phase 5 – TaktRequest-Erstellung vereinheitlichen

Aktuell existieren möglicherweise parallele Endpunkte:

```http
POST /projects/:projectId/takt-requests
POST /takt-requests
```

## Ziel

Es darf nur eine kanonische fachliche Implementierung zur Erstellung eines TaktRequests geben.

Beide Routen dürfen aus Kompatibilitätsgründen bestehen bleiben, müssen aber intern denselben Application Service verwenden.

Beispielsweise:

```text
createTaktRequestWithSnapshot()
```

## Verbindlicher Ablauf

Die Erstellung muss in einer Datenbanktransaktion ausführen:

1. Projektberechtigung prüfen
2. projektbezogene AN-Zuordnung prüfen
3. Takt und Taktversion prüfen
4. TaktRequest im Status `DRAFT` anlegen
5. unveränderlichen Snapshot erzeugen
6. Snapshot speichern
7. Commit

## Snapshot

Der Snapshot wird beim Erstellen des Requests erzeugt.

Entferne eine Logik, die beim späteren Versand ersatzweise einen Snapshot aus dem dann aktuellen Takt erzeugt.

Nicht zulässig:

```text
Request wurde ohne Snapshot erstellt
→ Takt wird später verändert
→ Versand erzeugt Snapshot aus verändertem Takt
```

## Falls Legacy-Daten ohne Snapshot existieren

Implementiere eine klar begrenzte Migrations- oder Reparaturlogik:

* nur für vorhandene historische Daten
* eindeutig markieren
* nicht für neue Requests verwenden
* dokumentieren, dass der Snapshot rekonstruiert wurde

## Tests

* beide Create-Routen verwenden denselben Service
* jeder neue Request besitzt genau einen Snapshot
* Snapshot entspricht der Taktversion beim Erstellen
* spätere Taktänderung verändert Snapshot nicht
* Versand erzeugt keinen neuen Ersatz-Snapshot
* AN eines anderen Projekts wird abgelehnt
* deaktivierte Projekt-AN-Zuordnung wird abgelehnt

# Phase 7 – Response-Idempotenz vollständig korrigieren

## Problem

Die Prüfung darf nicht nur `decision` vergleichen.

Speichere für jede fachliche Response einen deterministischen Hash über den vollständigen öffentlichen Payload.

Beispielsweise:

```text
responsePayloadHash
```

## Hash-Grundlage

Mindestens:

```text
schemaVersion
decision
reasonCode
comment
acceptedTimeWindow
alternatives
nextAvailableDate
```

## Kanonische Serialisierung

Implementiere rekursive kanonische JSON-Serialisierung:

* Objekt-Keys sortieren
* Objekte innerhalb von Arrays ebenfalls rekursiv kanonisieren
* Array-Reihenfolge beibehalten
* `undefined` eindeutig behandeln
* Datumswerte als ISO-Strings
* keine internen Felder einbeziehen

## Idempotenzregeln

### Gleicher Key und gleicher vollständiger Payload

* bestehende Response zurückgeben
* keine zweite Response
* keine zweite Nachricht
* keine zweite Statusänderung

### Gleicher Key und abweichender Payload

* `409 Conflict`
* keine Änderung

### Bereits bestehende Response ohne passenden Key

* keine zweite fachliche Response
* kontrollierte Konfliktantwort

## Outbox-Status

Wenn kein Outbox-Datensatz existiert:

Nicht verwenden:

```text
DELIVERED
```

Verwende stattdessen beispielsweise:

```text
NOT_SENT
UNKNOWN
MISSING_OUTBOX
```

oder eine vorhandene fachlich passende Darstellung.

## Tests

* gleicher vollständiger Payload ist idempotent
* gleiches `decision`, aber anderer Kommentar → Konflikt
* gleiches `decision`, aber anderes Zeitfenster → Konflikt
* gleiches `decision`, aber andere Alternative → Konflikt
* fehlende Outbox wird nicht als zugestellt gemeldet
* Retry verwendet dieselbe Nachricht

# Phase 8 – Response, Requeststatus und Outbox konsistent verarbeiten

## Ziel

Die fachliche Speicherung einer Response und der Statuswechsel des Requests müssen transaktional konsistent sein.

## Verbindliche Transaktion

Innerhalb einer Datenbanktransaktion:

1. Request mit Sperre laden
2. Organisationsberechtigung prüfen
3. Statusübergang prüfen
4. vorhandene Response prüfen
5. Response speichern
6. Alternativen speichern
7. Requeststatus aktualisieren
8. Outbox-Nachricht im Status `PENDING` anlegen
9. Commit

Erst danach erfolgt die technische Zustellung.

## Statusmapping

```text
ACCEPTED
→ Requeststatus ACCEPTED

ALTERNATIVES_PROPOSED
→ Requeststatus ALTERNATIVES_PROPOSED

REJECTED
→ Requeststatus REJECTED
```

## Nicht zulässig

* Response gespeichert, Requeststatus unverändert
* HTTP-Response meldet Status, der nicht in der Datenbank gespeichert ist
* Nachricht zugestellt, obwohl Response-Transaktion fehlgeschlagen ist
* Statusfehler wird lediglich geloggt und ignoriert

## Bei Transportfehler

* Response bleibt gespeichert
* Requeststatus bleibt fachlich korrekt
* Outbox wird `FAILED`
* API meldet fachliche Speicherung und technischen Fehler getrennt
* Retry erzeugt keine zweite Response

## Tests

* Response und Requeststatus werden gemeinsam gespeichert
* Fehler beim Statuswechsel rollt Response zurück
* Fehler beim Speichern einer Alternative rollt alles zurück
* Transportfehler verändert fachliche Daten nicht
* API liefert tatsächlich gespeicherten Status
* parallele Response-Erstellung erzeugt nur eine Response

# Phase 11 – Schema-Versionierung und Transport-Idempotenz korrigieren

## Unterstützte Version

Aktuell:

```text
1.0
```

Implementiere zentral:

```ts
assertSupportedSchemaVersion(schemaVersion)
```

## Regeln

* fehlende Version → `400`
* ungültiges Format → `400`
* unterstützte Version `1.0` → akzeptieren
* optionale unterstützte Minor-Version entsprechend dokumentierter Regel
* unbekannte Major-Version → `422` oder geeigneter klarer Fehler

Nicht ausreichend ist eine reine Regex-Prüfung wie:

```text
Zahl.Zahl
```

## Envelope-Idempotenz

Beim Vergleich derselben `messageId` müssen mindestens berücksichtigt werden:

```text
schemaVersion
messageType
senderOrgId
recipientOrgId
correlationId
causationId
payload
```

Gleiche `messageId` mit abweichender `schemaVersion` oder `causationId` muss als Konflikt gelten.

## Rekursive kanonische Serialisierung

Korrigiere `stableStringify()` so, dass:

* Objekt-Keys rekursiv sortiert werden
* Objekte in Arrays rekursiv sortiert werden
* verschachtelte Arrays korrekt verarbeitet werden
* keine unstabile Serialisierung durch JSONB-Roundtrips entsteht

## Tests

* Version `1.0` akzeptiert
* Version `99.0` abgelehnt
* gleiche Message mit anderer Version → Konflikt
* gleiche Message mit anderer `causationId` → Konflikt
* verschachtelte Objekte in Alternativen ergeben stabilen Hash
* JSONB-Roundtrip verändert Idempotenz nicht

# Phase 14 – Projektbezogene AN-Zuordnung konsequent verwenden

Ein AG besitzt mehrere Projekte.

Jedes Projekt kann unterschiedliche AN besitzen.

## Verbindliche Regel

Ein AN darf für einen TaktRequest nur ausgewählt werden, wenn:

* AN dem konkreten Projekt zugeordnet ist
* Zuordnung aktiv ist
* Zuordnung zeitlich gültig ist
* Gewerk oder Arbeitspaket passt, sofern angegeben

## Nicht zulässig

* globale Liste aller AN des AG
* AN eines anderen Projekts
* freie Eingabe beliebiger `anOrgId`
* Nutzung deaktivierter Zuordnung

## AG-Übersicht alle Projekte

* AG sieht alle eigenen Projekte

# Verbindliche Abschlusskriterien

Der Auftrag gilt nur als abgeschlossen, wenn alle folgenden Kriterien erfüllt sind:

* keine bekannte organisationsübergreifende Projektlücke
* keine ungeschützte interne Deadline-Route
* Revisionsrequest wird bei Transportfehler nicht als zugestellt markiert
* `responseRequiredBy` wird korrekt ausgegeben
* jeder neue Request besitzt genau einen unveränderlichen Snapshot
* nur eine kanonische Response-Fachlogik
* vollständige Payload-Idempotenz
* Response und Requeststatus sind transaktional konsistent
* Deadline Worker läuft automatisch oder als dokumentierter separater Prozess
* Rollen werden serverseitig geprüft
* unbekannte Major-Schema-Versionen werden abgelehnt
* Transport-Idempotenz berücksichtigt alle relevanten Envelope-Felder
* AN-Oberfläche enthält lokale Projekte, Buchungen und Availability Checks
* Reporting und Audit sind implementiert
* AG sieht eine Übersicht aller eigenen Projekte
* AG sieht pro Projekt alle dort zugeordneten AN
* Projekt A zeigt nicht die AN von Projekt B
* Frontendtests und Backendtests sind ausführbar
* Typecheck erfolgreich
* Build aller Anwendungen erfolgreich
* Dokumentation entspricht dem tatsächlichen Code
