# Replit-Auftrag – priorisierte Erweiterungen für Benutzerführung und Koordination

Arbeite im aktuellen Repository.

Ziel: Die bestehende AG-/AN-Koordination gezielt um sechs fachlich relevante Funktionen erweitern:

1. persönliches Aufgaben-Cockpit
2. Risk-/Constraint-Meldungen für vereinbarte Leistungen
3. Abhängigkeiten zwischen Leistungen und Change-Impact-Hinweise
4. Ready-for-Execution-Check
5. Clarification Requests
6. AG Coordination Board

Wichtig:

* bestehende Service-Request-, Change-Proposal-, Resource-Availability- und Dataspace-Logik weiterverwenden
* keine neue Workflow-Engine
* kein Event Sourcing
* keine automatische Terminfortschreibung
* keine Chat-Funktion
* keine neue EDC-Logik
* technische Bezeichnungen im Code Englisch
* UI-Texte Deutsch
* bestehende Legacy-`takt...`-Felder nicht unnötig migrieren
* neue Logik möglichst über wenige zentrale Services/Helper implementieren
* keine zusätzliche Architekturplanung durchführen

---

# 1. Persönliches Cockpit „Meine Aufgaben“

## Ziel

AG und AN sollen nach dem Login nicht zuerst technische Listen sehen, sondern alle aktuell notwendigen Aktionen.

Ergänze eine zentrale Ansicht:

```text
Meine Aufgaben
```

Diese Ansicht soll bestehende Daten aggregieren und keine neue Fachlogik duplizieren.

---

## Backend

Erstelle:

```text
artifacts/api-server/src/services/coordination-task-service.ts
```

Funktion:

```ts
getCoordinationTasks({
  orgId,
  role
})
```

Rückgabetyp:

```ts
type CoordinationTask = {
  id: string;

  serviceRequestId: string;
  serviceName: string;

  partnerOrgId: string;
  partnerName: string;

  projectId?: string | null;
  projectName?: string | null;

  taskType:
    | "RESPOND_TO_REQUEST"
    | "DECIDE_RESPONSE"
    | "RESPOND_TO_CHANGE_PROPOSAL"
    | "RESOLVE_CONSTRAINT"
    | "ANSWER_CLARIFICATION"
    | "CONFIRM_READINESS";

  priority:
    | "NORMAL"
    | "HIGH"
    | "CRITICAL";

  dueAt: string | null;

  status:
    | "OVERDUE"
    | "DUE_TODAY"
    | "DUE_SOON"
    | "OPEN";

  summary: string;

  lastChangedAt: string;

  targetUrl: string;
};
```

---

## Task-Erzeugungsregeln

### Eingehende Leistungsanfrage wartet auf AN

```text
taskType = RESPOND_TO_REQUEST
```

### AN hat geantwortet und AG muss entscheiden

```text
taskType = DECIDE_RESPONSE
```

### Change Proposal wartet auf Gegenseite

```text
taskType = RESPOND_TO_CHANGE_PROPOSAL
```

### Offener Constraint verlangt Aktion der eigenen Organisation

```text
taskType = RESOLVE_CONSTRAINT
```

### Offene Clarification wartet auf eigene Antwort

```text
taskType = ANSWER_CLARIFICATION
```

### Readiness Check verlangt Bestätigung

```text
taskType = CONFIRM_READINESS
```

Keine zusätzlichen Task-Typen einführen.

---

## Friststatus

Aus `dueAt` berechnen:

```text
OVERDUE
DUE_TODAY
DUE_SOON
OPEN
```

Definition:

```text
OVERDUE
= dueAt < now
```

```text
DUE_TODAY
= dueAt am heutigen Kalendertag
```

```text
DUE_SOON
= dueAt innerhalb der nächsten 3 Kalendertage
```

sonst:

```text
OPEN
```

---

## UI

Neue Start-/Dashboard-Sektion:

```text
Meine Aufgaben
```

Oben vier KPI-Karten:

```text
Überfällig
Heute fällig
Demnächst
Offen
```

Darunter Tabelle:

```text
Priorität
Vorgang
Partner
Aufgabe
Frist
Letzte Änderung
Aktion
```

Standard-Sortierung:

1. `OVERDUE`
2. `DUE_TODAY`
3. `DUE_SOON`
4. `CRITICAL`
5. `HIGH`
6. `lastChangedAt DESC`

Button in letzter Spalte:

```text
Öffnen
```

führt zu `targetUrl`.

Keine Aktionen direkt aus dem Dashboard ausführen.

# 2. Risk-/Constraint-Meldungen für vereinbarte Leistungen

## Ziel

AG oder AN sollen bei einer bereits vereinbarten Leistung ein Problem melden können, ohne sofort den vereinbarten Zeitraum zu verändern.

Ein Constraint bedeutet:

```text
Die aktuelle Vereinbarung besteht weiter,
aber ihre Ausführung ist gefährdet.
```

---

## Datenmodell

Erstelle Tabelle:

```text
service_constraints
```

Felder:

```ts
id
serviceRequestId

reportedByOrgId
reportedByRole // AG | AN

constraintType

description

status

responsibleOrgId

reportedAt
resolvedAt

createdAt
updatedAt
```

---

## `constraintType`

Nur:

```text
UPSTREAM_NOT_READY
SITE_NOT_READY
RESOURCE_CONFLICT
MATERIAL_NOT_AVAILABLE
INFORMATION_MISSING
APPROVAL_MISSING
ACCESS_RESTRICTED
SAFETY_CLEARANCE_MISSING
OTHER
```

---

## `status`

Nur:

```text
OPEN
RESOLVED
CANCELLED
```

---

## Regeln

Constraint darf nur erstellt werden, wenn:

```text
serviceRequest.currentAgreement != null
```

AG oder AN des Service Requests dürfen melden.

Beim Erstellen:

```text
agreedStart/agreedEnd NICHT verändern
```

Der Constraint ist nur ein Risikohinweis.

---

## API

Endpunkte:

```text
POST /service-requests/:id/constraints
GET  /service-requests/:id/constraints
POST /service-requests/:id/constraints/:constraintId/resolve
POST /service-requests/:id/constraints/:constraintId/cancel
```

Create Payload:

```ts
{
  constraintType: ConstraintType;
  description: string;
  responsibleOrgId: string;
}
```

Validieren:

```text
description nicht leer
responsibleOrgId muss AG oder AN des Vorgangs sein
```

---

## UI Detailseite

Direkt unter `Aktuelle Vereinbarung` anzeigen:

Wenn kein Constraint:

```text
Keine offenen Risiken
```

Wenn offen:

```text
⚠ Ausführung gefährdet
```

Darunter:

```text
Ressourcenkonflikt
gemeldet durch AN
verantwortlich: AN
seit 21.08.2026
```

Aktionen:

```text
[Als gelöst markieren]
[Terminänderung vorschlagen]
```

`Terminänderung vorschlagen` öffnet den bereits vorhandenen Change-Proposal-Dialog.

Keine neue Terminänderungslogik implementieren.

# 3. Abhängigkeiten zwischen Leistungen und Change Impact

## Ziel

Bei Terminänderungen soll sichtbar werden, welche nachgelagerten Leistungen möglicherweise betroffen sind.

Keine automatische Terminverschiebung.

---

## Datenmodell

Erstelle:

```text
service_dependencies
```

Felder:

```ts
id

projectId

predecessorServiceRequestId
successorServiceRequestId

dependencyType

lagDays

createdAt
updatedAt
```

---

## `dependencyType`

Nur:

```text
FINISH_TO_START
```

Für den PoC keine weiteren Abhängigkeitstypen.

`lagDays`:

```text
integer >= 0
```

---

## API

Endpunkte:

```text
POST   /projects/:projectId/service-dependencies
GET    /projects/:projectId/service-dependencies
DELETE /projects/:projectId/service-dependencies/:id
```

Create Payload:

```ts
{
  predecessorServiceRequestId: string;
  successorServiceRequestId: string;
  lagDays?: number;
}
```

Validieren:

* beide Service Requests gehören zum selben Projekt
* predecessor != successor
* keine direkte Duplikatabhängigkeit
* keine einfache Zirkelschleife erzeugen

Für Zyklen reicht DFS/BFS über die vorhandenen Dependencies.

Keine komplexe Scheduling Engine.

---

## Impact-Service

Erstelle:

```text
artifacts/api-server/src/services/change-impact-service.ts
```

Funktion:

```ts
evaluateChangeImpact({
  serviceRequestId,
  proposedStart,
  proposedEnd
})
```

Rückgabe:

```ts
type ChangeImpact = {
  affectedServices: Array<{
    serviceRequestId: string;
    serviceName: string;

    currentStart: string | null;
    currentEnd: string | null;

    requiredEarliestStart: string;

    impactDays: number;
  }>;
};
```

---

## Berechnung

Für jede direkte nachgelagerte Leistung:

```text
requiredEarliestStart
=
proposedEnd des Vorgängers
+ lagDays
+ 1 Kalendertag
```

Falls:

```text
successor.agreedStart < requiredEarliestStart
```

ist sie potenziell betroffen.

`impactDays`:

```text
requiredEarliestStart - successor.agreedStart
```

Nur direkte Nachfolger für den ersten Stand.

Keine rekursive automatische Verschiebung.

---

## UI Change Proposal

Vor dem Absenden eines AG-Change-Proposals:

```text
Auswirkungen prüfen
```

automatisch anzeigen.

Beispiel:

```text
⚠ 2 nachgelagerte Leistungen möglicherweise betroffen

Elektroinstallation
vereinbart ab 15.09.
frühester Start nach Änderung: 18.09.
+3 Tage

Malerarbeiten
vereinbart ab 20.09.
frühester Start nach Änderung: 22.09.
+2 Tage
```

Nur Hinweis.

Keine Checkbox:

```text
alle automatisch verschieben
```

implementieren.

# 4. Ready-for-Execution-Check

## Ziel

Kurz vor Ausführung soll erkennbar sein, ob die vereinbarte Leistung tatsächlich startbereit ist.

Keine komplexe Checklisten-Engine.

---

## Datenmodell

Erstelle:

```text
service_readiness_checks
```

Ein Datensatz pro Service Request.

Felder:

```ts
id
serviceRequestId

scheduleConfirmed
siteReady
informationComplete
agReady
anReady

updatedByOrgId

createdAt
updatedAt
```

Boolean-Felder.

---

## Gesamtstatus

Zentral berechnen:

```ts
type ReadinessStatus =
  | "READY"
  | "NOT_READY";
```

Regel:

```text
READY
nur wenn alle 5 Werte true
```

sonst:

```text
NOT_READY
```

Keine dritte Stufe.

---

## Verantwortlichkeiten

AG darf ändern:

```text
scheduleConfirmed
siteReady
informationComplete
agReady
```

AN darf ändern:

```text
anReady
```

AN darf die AG-Felder nur lesen.

AG darf `anReady` nur lesen.

Serverseitig erzwingen.

---

## API

```text
GET /service-requests/:id/readiness
PATCH /service-requests/:id/readiness
```

PATCH nur erlaubte Felder je Rolle.

---

## UI

Auf Detailseite neue kompakte Box:

```text
Ausführungsbereitschaft
```

Darstellung:

```text
✓ Termin bestätigt
✓ Arbeitsbereich bereit
⚠ Informationen vollständig
✓ AG bereit
✓ AN bereit
```

Gesamt:

```text
✓ Bereit zur Ausführung
```

oder:

```text
⚠ Noch nicht ausführungsbereit
```

Keine frei konfigurierbaren Checklistenpunkte.

---

## Task-Integration

Wenn `agreedStart` innerhalb der nächsten 7 Tage liegt und Readiness nicht vollständig ist:

Task erzeugen.

Für AG:

```text
CONFIRM_READINESS
```

wenn eines seiner Felder false ist.

Für AN:

```text
CONFIRM_READINESS
```

wenn `anReady = false`.

# 5. Clarification Requests

## Ziel

Fehlende Informationen sollen geklärt werden können, ohne daraus sofort eine Terminänderung zu machen.

Keine Chat-Funktion.

---

## Datenmodell

Erstelle:

```text
service_clarifications
```

Felder:

```ts
id
serviceRequestId

askedByOrgId
askedByRole

category

question
answer

status

answeredByOrgId

createdAt
answeredAt
updatedAt
```

---

## `category`

Nur:

```text
PLAN
APPROVAL
DIMENSION
ACCESS
INTERFACE_INFORMATION
SCOPE
OTHER
```

---

## `status`

Nur:

```text
OPEN
RESOLVED
CANCELLED
```

---

## API

```text
POST /service-requests/:id/clarifications
GET  /service-requests/:id/clarifications
POST /service-requests/:id/clarifications/:clarificationId/answer
POST /service-requests/:id/clarifications/:clarificationId/cancel
```

Create:

```ts
{
  category: ClarificationCategory;
  question: string;
}
```

Answer:

```ts
{
  answer: string;
}
```

---

## Regeln

AG oder AN dürfen Frage stellen.

Nur Gegenseite darf antworten.

Beim Antworten:

```text
answer setzen
answeredByOrgId setzen
answeredAt = now
status = RESOLVED
```

Keine Kommentare oder Threads.

Eine Frage → eine Antwort.

---

## UI

Auf Service-Request-Detailseite:

```text
Offene Klärungen
```

Beispiel:

```text
PLAN
Welche Planversion ist für Bereich B verbindlich?
gestellt durch AN · 21.08.
```

Button für Gegenseite:

```text
[Antworten]
```

Nach Resolution kompakt in Historie anzeigen.

---

## Task-Integration

Offene Clarification erzeugt Task bei der Gegenseite:

```text
ANSWER_CLARIFICATION
```

Nach Antwort verschwindet Task.

# 6. AG Coordination Board

## Ziel

AG soll alle Partner und Leistungen eines Projekts in einer einzigen Koordinationsübersicht sehen.

Keine Gantt-Planung.

Keine Ressourceninformationen des AN anzeigen.

---

## Backend

Erstelle:

```text
artifacts/api-server/src/services/ag-coordination-board-service.ts
```

Funktion:

```ts
getProjectCoordinationBoard({
  projectId,
  agOrgId
})
```

Rückgabe pro Service Request:

```ts
type CoordinationBoardItem = {
  serviceRequestId: string;
  serviceName: string;

  partnerOrgId: string;
  partnerName: string;

  agreedStart: string | null;
  agreedEnd: string | null;

  proposedStart: string | null;
  proposedEnd: string | null;

  proposalInitiator: "AG" | "AN" | null;

  nextActionOwner: "AG" | "AN" | "NONE";
  nextAction: string;

  responseRequiredBy: string | null;

  openConstraintCount: number;
  openClarificationCount: number;

  readinessStatus:
    | "READY"
    | "NOT_READY"
```

---
