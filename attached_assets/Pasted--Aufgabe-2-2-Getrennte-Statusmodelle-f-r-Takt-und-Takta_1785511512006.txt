# Aufgabe 2.2 – Getrennte Statusmodelle für Takt und Taktanfrage definieren

Ergänze getrennte fachliche Statusmodelle für:

* den Lebenszyklus eines Takts
* den Abstimmungsprozess einer Taktanfrage

Bearbeite:

* die zentrale OpenAPI-Spezifikation
* eine geeignete zentrale Domain- oder Typdatei
* die neue Dokumentationsdatei `docs/state-model.md`

Nimm noch keine Änderungen an Datenbanktabellen, bestehenden Delegation-Endpunkten oder Benutzeroberflächen vor.

## Ziel

Der Zustand eines Takts muss vom Zustand einer einzelnen Anfrage getrennt werden.

Ein technisch zugestellter, abgelehnter oder ersetzter Request darf nicht automatisch denselben Zustand am Takt auslösen.

## Enum `TaktLifecycleStatus`

Definiere folgende Werte:

```text
DRAFT
PLANNED
IN_COORDINATION
CONFIRMED
CANCELLED
```

Dokumentiere die Bedeutung:

* `DRAFT` – Der Takt wird bearbeitet.
* `PLANNED` – Der Takt ist planungsseitig vorbereitet.
* `IN_COORDINATION` – Mindestens eine Abstimmung mit einem Nachunternehmer läuft.
* `CONFIRMED` – Der Takt wurde fachlich bestätigt.
* `CANCELLED` – Der Takt wurde aufgehoben.

## Übergangsfunktion

Implementiere eine kleine, frameworkunabhängige Domain-Funktion:

```ts
isValidTaktRequestTransition(
  currentStatus: TaktRequestStatus,
  nextStatus: TaktRequestStatus
): boolean
```

Ergänze außerdem eine Funktion, die bei einem ungültigen Übergang einen klaren Fehler auslöst, beispielsweise:

```ts
assertValidTaktRequestTransition(
  currentStatus: TaktRequestStatus,
  nextStatus: TaktRequestStatus
): void
```

Verwende den bestehenden Stil für Domain-Fehler.

## Fachliche Regeln

Dokumentiere ausdrücklich:

1. `DELIVERED` ist nur ein technischer Zustellstatus.
2. `DELIVERED` bedeutet keine fachliche Zustimmung.
3. `ACCEPTED` ist eine fachliche Bestätigung.
4. `REJECTED` bezieht sich nur auf die konkrete Anfrage.
5. Eine abgelehnte Anfrage setzt den Takt nicht automatisch auf `CANCELLED`.
6. Eine nicht akzeptierte Alternative führt zu `REVISION_REQUIRED`.
7. Eine neue Anfrageversion setzt die vorherige Anfrage auf `SUPERSEDED`.
8. Eine offene Anfrage kann den Takt auf `IN_COORDINATION` setzen.
9. Erst eine akzeptierte Antwort oder Alternative kann den Takt auf `CONFIRMED` setzen.
10. Der Taktstatus darf nicht direkt aus einem Transportstatus abgeleitet werden.
