# Replit-Auftrag – AN-Ressourcenübersicht, Kapazitätsplanung, Resource-Gantt und Anfragekonflikte

Arbeite im aktuellen Repository.

Ziel: Die AN-Seite so erweitern, dass der Nutzer auf einen Blick sieht:

1. welche Ressourcen insgesamt vorhanden sind,
2. welche Kapazitäten fest eingeplant sind,
3. welche Kapazitäten durch offene Anfragen potenziell beansprucht werden,
4. welche Kapazitäten noch frei sind,
5. wo konkrete Anfragen Konflikte erzeugen,
6. welcher nächste Zeitraum vollständig verfügbar wäre,
7. wie bestätigte, tentative und angefragte Ressourcen zeitlich in einer Resource-Timeline/Gantt liegen.

Wichtig:

* bestehende `ResourceType`-/`Resource`-/`ResourceBooking`-/Availability-Logik wiederverwenden
* keine parallele Ressourcenlogik implementieren
* bestehende Dataspace-/Service-Request-Logik nicht verändern
* keine interne Ressourcendaten an den AG übertragen
* technische Bezeichner im Code Englisch
* UI-Texte Deutsch
* keine komplexe Projekt-Gantt-Planungssoftware bauen
* Gantt ausschließlich als **Resource Timeline** für AN-interne Ressourcenplanung verwenden

# 2. Tab „Übersicht“ – kompakte Gesamtübersicht aller Ressourcen

Ziel: Schneller Bestands- und Auslastungsüberblick.

Oberhalb der Tabelle vier KPI-Karten:

```text
Ressourcentypen
Konkrete Ressourcen
Aktive Buchungen
```

# 3. Backend-Service für kompakte Ressourcenübersicht

Erstelle bzw. erweitere:

```text
artifacts/api-server/src/services/resource-capacity-overview-service.ts
```

Funktion:

```ts
getResourceCapacityOverview({
  orgId,
  startDate,
  endDate
})
```

Rückgabe pro `ResourceType`:

```ts
type ResourceCapacityOverviewItem = {
  resourceTypeId: string;
  resourceTypeName: string;
  capacityUnit: string;

  resourceCount: number;

  totalCapacity: number;
  confirmedCapacity: number;
  requestedCapacity: number;

  availableCapacity: number;
  projectedAvailableCapacity: number;

  utilizationPercent: number;
};
```

Berechnung:

```text
totalCapacity
= Summe Resource.capacity aller aktiven Resources dieses ResourceType
```

```text
confirmedCapacity
= effektive Kapazität aller CONFIRMED Bookings im ausgewählten Zeitraum
```

```text
requestedCapacity
= effektive Kapazität aus TENTATIVE Bookings
  plus offenen Service-Request-Requirements,
  sofern dafür noch kein Tentative Booking existiert
```

```text
availableCapacity
= totalCapacity - confirmedCapacity
```

```text
projectedAvailableCapacity
= totalCapacity - confirmedCapacity - requestedCapacity
```

Negative Werte zulassen.

```text
utilizationPercent
= confirmedCapacity / totalCapacity * 100
```

Bei `totalCapacity = 0`:

```text
utilizationPercent = 0
```

---

# 4. Offene Anforderungen nicht doppelt zählen

Wichtig:

Wenn für dieselbe offene Service Request / dasselbe Requirement bereits ein:

```text
TENTATIVE ResourceBooking
```

existiert, den Requirement-Bedarf nicht zusätzlich in `requestedCapacity` addieren.

Regel:

```text
Tentative Booking vorhanden
→ Tentative Booking verwenden

kein Tentative Booking vorhanden
→ offenen Requirement-Bedarf verwenden
```

Keine Doppelzählung.

---

# 5. Requirement-Zeitraum berücksichtigen

Bei offenen Anforderungen immer:

```text
periodStart
periodEnd
```

verwenden.

Nicht automatisch den kompletten Service-Request-Zeitraum verwenden.

Beispiel:

```text
Service Request:
01.–20.09.

Mobilkran Requirement:
10.–12.09.
```

Dann nur 10.–12.09. als angefragte Krankapazität berücksichtigen.

---

# 6. `utilizationPercent` berücksichtigen

Für Aggregationen:

```text
effectiveRequirement =
requiredCapacity * utilizationPercent / 100
```

Für Bookings:

```text
effectiveBooking =
quantity bzw. resource.capacity
* utilizationPercent / 100
```

UI zeigt weiterhin die fachliche Originalangabe:

```text
6 Personen · 50 %
```

und nicht nur:

```text
3
```

# 21. Einheitliche Availability-Zustände

Zentral definieren:

```ts
type CapacityStatus =
  | "AVAILABLE"
  | "AT_RISK"
  | "CONFLICT";
```

UI:

```text
✓ Verfügbar
⚠ Gefährdet
✕ Konflikt
```

Bedeutung:

```text
AVAILABLE
= Request gegen bestätigte Buchungen machbar
  und offene Anfragen verursachen keinen Konflikt
```

```text
AT_RISK
= gegen bestätigte Buchungen machbar,
  aber inklusive offener/tentativer Anforderungen potenziell nicht mehr
```

```text
CONFLICT
= bereits gegen bestätigte Buchungen nicht machbar
```
