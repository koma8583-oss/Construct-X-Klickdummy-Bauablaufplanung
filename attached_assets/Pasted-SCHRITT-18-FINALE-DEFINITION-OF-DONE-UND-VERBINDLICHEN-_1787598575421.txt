SCHRITT 18 – FINALE DEFINITION OF DONE UND VERBINDLICHEN ABSCHLUSSBERICHT ERSTELLEN

ZIEL

Die Umsetzung gilt erst als abgeschlossen, wenn der gesamte Prozess fachlich, technisch und hinsichtlich der logischen Organisationsisolation konsistent ist.


DEFINITION OF DONE

Alle folgenden Aussagen müssen wahr sein:

1. Es wird weiterhin EINE gemeinsame verwaltete PostgreSQL-Datenbank verwendet.

2. Es wurden KEINE getrennten PostgreSQL-Benutzer für AG, AN oder Hub eingeführt.

3. Es wurden KEINE getrennten Connection Strings je Organisation eingeführt.

4. AG und AN verwenden dieselbe technische DB-Infrastruktur.

5. Die Datentrennung erfolgt logisch im Application Layer.

6. Private Datensätze besitzen einen ownerOrgId- bzw. gleichwertigen Organisationsscope.

7. currentOrgId stammt aus dem Auth-/Application Context.

8. ownerOrgId kann nicht vom Client frei manipuliert werden.

9. AG kann keine privaten AN-owned Rows über reguläre Services lesen.

10. AN kann keine privaten AG-owned Rows über reguläre Services lesen.

11. Participant Directory ist bewusst geteilt und enthält nur freigegebene Discovery-Metadaten.

12. „Zum Projekt einladen“ nutzt Participant Directory.

13. Neue Einladungen verwenden participantId als externe Identität.

14. AG Project Membership und AN Project Invitation sind getrennte logische Domain-Sichten.

15. AG Membership INVITED erzeugt nicht direkt eine AN Invitation.

16. Erst PROJECT_INVITATION Inbound erzeugt AN Invitation PENDING.

17. AN Acceptance ändert keine AG Membership direkt.

18. Erst PROJECT_INVITATION_RESPONSE Inbound setzt AG Membership ACTIVE.

19. PROJECT_INVITATION wird transactional über eine AG-owned Outbox erzeugt.

20. PROJECT_INVITATION_RESPONSE wird transactional über eine AN-owned Outbox erzeugt.

21. Failed Invitation kann AG retryen.

22. Failed Response kann AN retryen.

23. PROJECT_MEMBERSHIP Policy wird tatsächlich geprüft.

24. Externe Nachrichten verwenden Participant IDs.

25. OpenAPI und Server-Routen stimmen überein.

26. Der generierte Client verwendet die korrekte Invite-Route.

27. ACTIVE Project Membership ist das zentrale Projektbeitritts-Gate.

28. project_contractors ist kein zweites verstecktes ACTIVE-Gate.

29. ACTIVE Membership ermöglicht die spätere Leistungszuordnung.

30. SERVICE_REQUEST folgt ebenfalls der organisationsgetrennten Datenraumkommunikation.

31. AN liest nicht direkt die AG-owned ServiceRequest-Row.

32. AG liest nicht direkt AN ResourcePlanning/ResourceBookings.

33. Change Proposal, Clarification, Constraint und Readiness wurden auf Shared-DB-Cross-Org-Shortcuts geprüft.

34. Withdrawal/Revocation läuft ebenfalls über DataspaceExchange.

35. Business Audit ist organisationsgescoped.

36. Transport Audit ist organisationsgescoped.

37. Cross-Org-Read-Regressionstests sind vorhanden.

38. Shared-DB-Bypass-Tests sind vorhanden.

39. End-to-End Invite → Accept → Service Request funktioniert ohne ACTIVE project_contractors Seed.

40. Workspace Typecheck PASS.

41. Workspace Tests PASS.

42. Workspace Build PASS.

VERBINDLICHE ARCHITEKTURFORMULIERUNG

EINE PostgreSQL-Datenbank.
EINE bestehende verwaltete technische Datenbankverbindung.
KEINE PostgreSQL-Benutzertrennung zwischen AG, AN und Hub.

Die organisatorische Datensouveränität erfolgt logisch über:

Authentifizierung
→ currentOrgId
→ ownerOrgId
→ Service-/Repository-Scope
→ Authorization.

Der fachlich vorgesehene organisationsübergreifende Übergang erfolgt ausschließlich über:

DataspaceExchange
→ Participant Identity
→ Policy
→ Nachricht
→ Inbound Processor
→ lokale organisationsbezogene Sicht.
