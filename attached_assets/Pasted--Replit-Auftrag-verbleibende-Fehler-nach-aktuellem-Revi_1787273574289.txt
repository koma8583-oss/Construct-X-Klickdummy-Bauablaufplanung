# 1. P0 – eintägige Leistungen zulassen

Prüfe:

```text
artifacts/api-server/src/lib/takt-request-snapshot-service.ts
```

Aktuell werden Leistungen mit:

```text
plannedStart == plannedEnd
```

noch abgelehnt.

Fachliche Regel:

```text
plannedStart = inklusiv
plannedEnd   = inklusiv
```

Damit muss beispielsweise:

```text
21.08.2026 – 21.08.2026
```

ein gültiger eintägiger Zeitraum sein.

Ändere daher eine Prüfung wie:

```ts
plannedEnd <= plannedStart
```

zu:

```ts
plannedEnd < plannedStart
```

Bestehende Working-Day-Logik nicht verändern.

# 2. Datumslogik konsistent halten

Prüfe gemeinsam:

```text
working-days.ts
takt-request-snapshot-service.ts
availability-check-service.ts
alternative-generator.ts
```

Planungsdaten bleiben fachlich inklusiv:

```text
[startDate, endDate]
```

Für interne Timestamp-Überlappungen verwenden:

```text
[startOf(startDate), startOf(dayAfter(endDate)))
```

Beispiel:

```text
01.09.–05.09.
```

intern:

```text
01.09. 00:00
bis
06.09. 00:00 exklusiv
```

Falls `parseInclusiveEnd()` oder ein vergleichbarer Helper bereits existiert, diesen wiederverwenden.

Keine zweite Datumslogik hinzufügen.

# 3. P0 – Alternative Generator auf DTC-Requirements umstellen

Prüfe:

```text
artifacts/api-server/src/services/availability-check-service.ts
artifacts/api-server/src/services/alternative-generator.ts
```

Aktuelles Problem:

Die normale DTC-Verfügbarkeitsprüfung berücksichtigt inzwischen:

```text
resourceTypeId
requiredCapacity
utilizationPercent
requiredQualification
periodStart
periodEnd
```

Der Alternative Generator verwendet jedoch noch überwiegend Legacy-Logik auf Basis konkreter:

```text
resourceId
EMPLOYEE
CREW
EQUIPMENT
MACHINE
```

Das darf für DTC-basierte Anforderungen nicht mehr die entscheidende Prüfung sein.

## Ziel

Eine Alternative ist nur gültig, wenn **alle ResourceRequirements der Anfrage** im Kandidatenzeitraum verfügbar sind.

Prüfe für jede Alternative:

```text
ResourceType
benötigte Kapazität
Auslastung
Qualifikation
Requirement-Zeitraum
bestehende Typbuchungen
bestehende konkrete Buchungen
```

---

# 4. Keine doppelte Availability-Logik

Nicht eine zweite neue Kapazitätsberechnung im `alternative-generator.ts` implementieren.

Extrahiere die bereits funktionierende DTC-Prüfung möglichst in eine kleine interne Funktion, beispielsweise:

```ts
evaluateResourceRequirements(...)
```

oder:

```ts
evaluateRequirementsForWindow(...)
```

Diese Funktion soll sowohl für:

```text
ursprünglichen Zeitraum
```

als auch für:

```text
Alternativzeitraum
```

verwendet werden.

Damit müssen normale Verfügbarkeitsprüfung und Alternativprüfung dieselben Regeln nutzen.

---

# 5. Typbasierte Buchungen bei Alternativen berücksichtigen

Eine Buchung wie:

```text
resourceId = null
resourceTypeId = Facharbeiter Trockenbau
quantity = 4
utilizationPercent = 100
```

muss die verfügbare Kapazität dieses Ressourcentyps auch im Alternative Generator reduzieren.

Nicht nur `resourceId`-basierte Bookings prüfen.

Für Typbuchungen weiterhin rechnen:

```text
verbrauchte Kapazität =
quantity × utilizationPercent / 100
```

---

# 6. Vollständigen Alternativ-Suchhorizont berücksichtigen

Wenn Alternativen beispielsweise bis zu 60 Tage nach vorne gesucht werden, müssen auch Buchungen aus diesem Zeitraum berücksichtigt werden.

Nicht nur Bookings des ursprünglichen Taktes laden.

Mindestens:

```text
originalStart
bis
maxAlternativeEnd
```

berücksichtigen.

Eine Alternative darf niemals als verfügbar erscheinen, wenn im Kandidatenzeitraum bereits eine relevante bestätigte Buchung liegt.

# 7. P0 – ACCEPT_ALTERNATIVE neu bewerten

Prüfe:

```text
artifacts/api-server/src/services/gu-decision-service.ts
```

Aktuelles Problem:

Bei:

```text

```

werden weiterhin `availableResources` aus dem ursprünglichen Availability Check verwendet.

## Zielworkflow

Bei `ACCEPT_ALTERNATIVE`:

```text

2. alle ResourceRequirements der Anfrage laden
3. diese Requirements für den akzeptierten Zeitraum erneut prüfen
4. nur wenn vollständig machbar → Buchungen erzeugen
5. alle notwendigen ResourceTypes buchen
```

Nicht die `availableResources` des ursprünglichen Zeitfensters wiederverwenden.

Die Erstellung aller notwendigen Buchungen möglichst in einer bestehenden DB-Transaktion durchführen.

# 9. Typbasierte Auto-Bookings verwenden

Für DTC ResourceRequirements weiterhin keine automatische konkrete Mitarbeiterauswahl durchführen.

# 10. Requirement-Kapazität und Auslastung unverändert in Booking übernehmen

Aktuell darf nicht mehr aus:

```text
requiredCapacity = 6
utilizationPercent = 50
```

werden:

```text
quantity = 3
utilizationPercent = 100
```

Bevorzugt übernehmen:

```text
quantity = requiredCapacity
utilizationPercent = requirement.utilizationPercent
```

Also:

```text
Requirement:
6 Personen × 50 %

Booking:
6 Personen × 50 %
```

Keine `Math.ceil()`-Transformation der effektiven Kapazität für das Auto-Booking verwenden.

Die effektive Kapazität wird nur für die Verfügbarkeitsberechnung verwendet.
