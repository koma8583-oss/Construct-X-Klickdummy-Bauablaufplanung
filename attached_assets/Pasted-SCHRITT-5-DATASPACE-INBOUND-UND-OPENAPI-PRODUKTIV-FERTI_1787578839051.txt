SCHRITT 5 – DATASPACE INBOUND UND OPENAPI PRODUKTIV FERTIGSTELLEN

ZIEL

Die vorhandene Dataspace-Inbound-Struktur darf nicht nur aus ungenutztem Code bestehen.

Eingehende Service Requests und Service Responses müssen:

- über einen tatsächlich registrierten Endpoint eintreffen,
- idempotent verarbeitet werden,
- einen echten Domain-Service aufrufen,
- nur nach erfolgreicher Domain-Verarbeitung als PROCESSED markiert werden.

Zusätzlich müssen die vorhandenen Coordination APIs in OpenAPI beschrieben werden.

Prüfe insbesondere:

- routes/dataspace-inbound.ts
- routes/index.ts
- rest-dataspace-exchange.ts
- inbound-exchange-service.ts
- DataspaceExchange Interface
- Domain Services für eingehende Service Requests / Responses
- new LocalHubTransport()
- lib/api-spec/openapi.yaml
- bestehende API-Codegen-Scripts


1. DATASPACE-INBOUND-ROUTER PRODUKTIV REGISTRIEREN

Prüfen, ob:

routes/dataspace-inbound.ts

im zentralen Router tatsächlich importiert und registriert wird.

Falls nicht:

entsprechend bestehender Routerstruktur registrieren.

Beispiel sinngemäß:

import { dataspaceInboundRouter }
  from "./dataspace-inbound";

router.use(dataspaceInboundRouter);

oder mit bestehendem Prefix:

router.use(
  "/dataspace/inbound",
  dataspaceInboundRouter
);

Nicht doppelte Prefixes erzeugen.

Die tatsächlich vorhandene Route-Struktur berücksichtigen.


2. ROUTE-LAUFZEITTEST

Nach Registrierung muss mindestens erreichbar sein:

POST .../dataspace/inbound/service-requests

POST .../dataspace/inbound/service-responses

entsprechend tatsächlich definierten Pfaden.

Test über API-Integration, nicht nur Router-Unit-Test.


3. DataspaceExchange INTERFACE VOLLSTÄNDIG MACHEN

Falls das Interface aktuell nur publish-Methoden definiert, aber die Implementierung zusätzlich:

receiveServiceRequest(...)
receiveServiceResponse(...)

besitzt:

diese Receive-Methoden in das zentrale Interface aufnehmen.

Damit Consumer nicht gegen konkrete RestDataspaceExchange-Klasse programmieren müssen.


4. RECEIVE DARF NICHT MIT undefined PROCESSOR AUFGERUFEN WERDEN

Aktuell darf kein Pfad existieren wie:

receiveServiceRequest(
  payload,
  undefined
)

wenn anschließend:

PROCESSED

gesetzt wird.

Für eingehende Service Requests einen echten Processor übergeben.

Beispiel:

await exchange.receiveServiceRequest(
  payload,
  async (validatedPayload) => {
    await incomingServiceRequestService.process(
      validatedPayload
    );
  }
);

Analog für Service Response.


5. BESTEHENDE DOMAIN-SERVICES VERWENDEN

Keine zweite Request-/Response-Persistenzlogik im Dataspace-Route-Handler implementieren.

Route:

- Authentifizierung / Transportvalidierung
- Payload Parsing
- DataspaceExchange.receive...

Processor:

- vorhandenen Domain Service aufrufen

Domain Service:

- eigentliche fachliche Speicherung / Statusänderung

Keine doppelte Businesslogik im Transport Layer.


6. SERVICE REQUEST INBOUND FLOW

Soll logisch exakt sein:

HTTP Receive

→ Payload validieren

→ messageId bestimmen

→ Inbound Idempotency Claim

→ Status RECEIVED

→ vorhandenen Domain Service aufrufen

→ Request fachlich erzeugen/aktualisieren

→ Status PROCESSED

→ Success Response


7. SERVICE RESPONSE INBOUND FLOW

Analog:

HTTP Receive

→ Payload validieren

→ Idempotency Claim

→ RECEIVED

→ vorhandenen Response Domain Service

→ Response fachlich speichern

→ PROCESSED


8. DOMAIN-FEHLER

Wenn Domain-Verarbeitung fehlschlägt:

Status:

FAILED

setzen.

Fehler nicht als PROCESSED markieren.

HTTP-Fehler gemäß bestehender Error-Struktur zurückgeben.


9. DUPLICATE-BEHANDLUNG

Wenn messageId bereits:

PROCESSED

ist:

keine zweite Domain-Verarbeitung.

Route soll einen echten Duplicate-Zustand zurückgeben können.

Beispiel:

{
  status: "DUPLICATE",
  messageId: ...
}

oder vorhandenes äquivalentes Schema.


10. UNGENUTZTE duplicate-VARIABLE ENTFERNEN

Falls aktuell:

let duplicate = false;

existiert, aber niemals geändert wird:

entfernen und Ergebnis direkt aus Inbound-Service/Exchange ableiten.

Der Inbound-Service soll idealerweise zurückgeben:

{
  duplicate: boolean;
  status: "PROCESSED" | "DUPLICATE";
}

oder äquivalente Information.


11. FAILED RETRY

Falls bestehender Inbound-Service FAILED-Nachrichten neu claimen kann:

diese Funktionalität beibehalten.

Wichtig:

Gleiche messageId:

PROCESSED
→ nicht neu

RECEIVED in Bearbeitung
→ nicht parallel erneut

FAILED
→ entsprechend bestehender Retry-Regel erneut verarbeitbar


12. ATOMARE IDEMPOTENZ

Check-then-insert ohne Concurrency-Schutz vermeiden.

Bestehenden atomaren INSERT/ON CONFLICT-/Claim-Mechanismus verwenden.

Zwei parallele gleiche messageId dürfen Business Processing nur einmal ausführen.

Rein interner:

Im Abschlussbericht begründen.


16. OUTBOUND IDEMPOTENZ PRÜFEN

Falls vorhandene Publish-Logik:

→ return

nutzt:

zusätzlich prüfen, ob zwei parallele Calls dieselbe Nachricht zweimal versenden können.

Falls Insert Claim bereits atomar möglich ist:

nur der Gewinner darf tatsächlichen Send durchführen.

Keine große neue Architektur bauen.
