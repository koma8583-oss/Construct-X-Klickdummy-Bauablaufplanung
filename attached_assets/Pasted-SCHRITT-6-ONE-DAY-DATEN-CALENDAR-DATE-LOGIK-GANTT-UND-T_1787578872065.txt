1. ONE-DAY-ZEITFENSTER ÜBERALL ZULASSEN

Ein Leistungsvorgang darf genau einen Kalendertag dauern.

Fachliche Regel:

start <= end
→ gültig

Nur:

end < start
→ ungültig


2. AG ProposalActions KORRIGIEREN

Falls dort:

if (end <= start)

steht:

ändern auf Calendar-Date-Vergleich:

if (
  compareCalendarDates(end, start) < 0
)

oder vorhandenen äquivalenten Helper.


3. AN ProposalActions KORRIGIEREN

Identische Semantik.

Keine abweichende AN-Regel.


4. CHANGE IMPACT KORRIGIEREN

Auch dort:

start == end

zulassen.

Keine:

end <= start

Validierung.


5. REVISION UND ALTERNATIVEN PRÜFEN

Global alle Zeitfenster-Validatoren suchen.

Für fachliche Calendar-Day-Intervalle überall:

start <= end


6. ZENTRALEN Calendar-Date HELPER VERWENDEN

calendar-date-utils.ts

ist die zentrale Quelle.

Keine zusätzlichen gleichartigen lokalen Helper pflegen.

9. INKLUSIVE DAUER

Dauer einer Leistung:

differenceInCalendarDays(
  end,
  start
) + 1

Damit:

01.–01.
= 1 Tag

01.–05.
= 5 Tage


10. GANTT: FREIE RESOURCES SICHTBAR MACHEN

Aktuell darf keine Logik verbleiben wie:

if (!booksForThis.length) return;

Die Basis des Gantt muss aus:

allen aktiven Resources

gebildet werden.

Danach Bookings zuordnen.


11. VIEWMODEL ZUERST AUS RESOURCES

Sinngemäß:

const resourceRows =
  activeResources.map(resource => ({
    resource,
    bookings: ...
  }));

Nicht:

bookings
→ daraus Resources ableiten.


12. TYPE-LEVEL BOOKINGS NICHT VERWERFEN

Booking:

resourceId == null
resourceTypeId != null

ist ein gültiges Type-Level-Booking.

Keine:

if (!booking.resourceId) return;

Logik mehr, die diese Daten vollständig ausblendet.


13. TYPE-LEVEL BOOKING DARSTELLUNG

Pro ResourceType eine Aggregate-/Type-Level-Zeile verwenden.

Beispiel:

Facharbeiter Trockenbau
[Type-Level]

01.–05.
4 Personen @ 50 %

Keine künstliche Zuordnung auf konkrete Resource.


14. KEINE KONKRETEN AN-RESSOURCEN ERFINDEN

Type-Level Booking nicht automatisch auf einzelne Personen/Maschinen verteilen.

Nur aggregiert darstellen.


15. KONKRETE RESOURCE CONFLICT LOGIK KORRIGIEREN

Konflikt nicht aus:

Anzahl überlappender Bookings > 1

ableiten.

Stattdessen pro Kalendertag:

dailyUtilization =
  sum(utilizationPercent aller aktiven Bookings)


16. KONFLIKTREGEL

dailyUtilization <= 100
→ kein Konflikt

dailyUtilization > 100
→ Konflikt


17. STATUSREGEL

0 %
→ frei

1–99 %
→ teilweise belegt

100 %
→ voll belegt

>100 %
→ Konflikt

33. DST-/TIMEZONE-ROBUSTHEIT

Mindestens einen Calendar-Date-Test um ein Datum durchführen, an dem lokale DST-Probleme auftreten könnten.

Da fachlich reine YYYY-MM-DD-Daten verwendet werden:

Ergebnis muss unabhängig von DST genau korrekte Kalendertage liefern.
