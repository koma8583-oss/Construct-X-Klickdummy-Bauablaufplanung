GESAMTAUFTRAG – PROJEKTEINLADUNG ÜBER DEN DATENRAUM FACHLICH UND TECHNISCH KONSISTENT UMSETZEN

ZIELBILD

Die bestehende Projekteinladung soll vollständig auf das folgende fachliche Modell ausgerichtet werden:

1. Der AG sieht eine Liste verifizierter AN, die als Teilnehmer des Datenraums registriert sind.
2. Der AG wählt einen AN aus.
3. Der AG führt die Aktion „Zum Projekt einladen“ aus.
4. Auf AG-Seite entsteht eine lokale Projektmitgliedschaft mit Status INVITED.
5. Die Einladung wird als PROJECT_INVITATION über den DataspaceExchange übertragen.
6. Erst durch die Verarbeitung dieser Nachricht auf AN-Seite entsteht dort eine lokale Projekteinladung.
7. Der AN kann „Projekt beitreten“ oder „Ablehnen“.
8. Die Entscheidung des AN wird ausschließlich lokal auf AN-Seite gespeichert.
9. Die Entscheidung wird als PROJECT_INVITATION_RESPONSE über den DataspaceExchange an den AG übertragen.
10. Erst durch die Verarbeitung der ACCEPTED-Antwort auf AG-Seite wird die dortige Project Membership ACTIVE.
11. Erst danach darf der AG dem AN konkrete Leistungen zuordnen bzw. Leistungsanfragen senden.
12. Die spätere Leistungs- und Bauablaufkoordination läuft ebenfalls über den Datenraum.

WICHTIGER ARCHITEKTURGRUNDSATZ

Die Anwendung verwendet weiterhin:

- EINE gemeinsame verwaltete PostgreSQL-Datenbank
- denselben bestehenden technischen Datenbankzugang
- dieselbe bestehende Datenbankverbindung bzw. denselben Connection Pool

Es dürfen ausdrücklich NICHT eingeführt werden:

- getrennte PostgreSQL-Benutzer für AG, AN oder Hub
- getrennte Datenbankrollen als Mandantentrennung
- getrennte Connection Strings für AG und AN
- separate Datenbanken
- separate PostgreSQL-Schemas nur zur Mandantentrennung

AG, AN und Hub sind Anwendungsrollen bzw. Organisationskontexte und KEINE unterschiedlichen PostgreSQL-Benutzer.

Die Datensouveränität wird LOGISCH innerhalb derselben Datenbank umgesetzt:

Authentifizierung
→ currentOrgId
→ ownerOrgId
→ Service-/Repository-Filter
→ Authorization

Die gemeinsame Datenbank darf nicht als fachlicher Kommunikationskanal zwischen AG und AN verwendet werden.

Organisationsübergreifende fachliche Informationen dürfen ausschließlich über:

DataspaceExchange
→ Policy-/Identity-Prüfung
→ Nachricht
→ Inbound Processor
→ lokale organisationsbezogene Sicht

übertragen werden.

SCHRITT 1 – LOGISCHE ORGANISOLATION INNERHALB DER GEMEINSAMEN DATENBANK VERBINDLICH MACHEN
======================================================================

ZIEL

AG und AN verwenden dieselbe PostgreSQL-Datenbank, dürfen aber über reguläre Services niemals direkt auf private Datensätze der jeweils anderen Organisation zugreifen.

1. BESTEHENDES AUTHENTIFIZIERUNGSMODELL PRÜFEN

Ermittle, wie die aktuelle Organisation bestimmt wird.

Beispielsweise:

req.user.orgId
currentOrganization.id
authContext.orgId

Diese bestehende Quelle weiterverwenden.

Keine neue parallele Organisationsauflösung einführen.


2. currentOrgId VERBINDLICH AUS AUTH CONTEXT

Für private Domain-APIs:

const currentOrgId = req.user.orgId;

oder vorhandenes Äquivalent.

Nicht akzeptieren:

{
  "ownerOrgId": "..."
}

als frei vom Client bestimmbaren Datenbesitzer.


3. ownerOrgId FÜR ORGANISATIONSSPEZIFISCHE DATEN

Private organisationsbezogene Rows benötigen einen eindeutigen Eigentümer.

Bevorzugt:

ownerOrgId

Falls im Bestand bereits eine andere eindeutige Tenant-Konvention existiert, diese konsistent weiterverwenden.

Keine unnötige zweite Benennung einführen.


4. PRIVATE QUERIES IMMER SCOPEN

Nicht:

SELECT ...
FROM project_invitations
WHERE id = ?

sondern:

SELECT ...
FROM project_invitations
WHERE id = ?
AND ownerOrgId = currentOrgId


5. DAS GILT FÜR LESEN UND SCHREIBEN

UPDATE/DELETE ebenfalls:

WHERE id = ?
AND ownerOrgId = currentOrgId


6. KEIN FRONTEND-FILTER ALS SICHERHEIT

Nicht:

Backend liefert alle Rows
→ Frontend filtert nach Organisation.

Filterung und Rechteprüfung müssen im Backend erfolgen.


7. KEINE CROSS-ORG-JOINS ZU PRIVATEN DATEN

AG darf nicht beispielsweise über einen Join direkt lesen:

AN ResourceBookings
AN interne Ressourcen
AN interne Projekte
AN ProjectInvitations

AN darf nicht direkt lesen:

AG Gesamtterminplanung
AG interne Projektinformationen
AG Memberships
AG interne Outbox


8. BEWUSST GETEILTE DATEN AUSNEHMEN

Participant Directory ist bewusst ein geteilter Datenraumdienst.

Dort dürfen beispielsweise sichtbar sein:

participantId
organizationName
organizationType
identityStatus
connectorEndpoint
capabilities

Dies erzeugt aber kein Zugriffsrecht auf private Domain-Daten.


9. KEINE POSTGRESQL-BENUTZERTRENNUNG

Nicht implementieren:

CREATE ROLE ag_user
CREATE ROLE an_user
CREATE ROLE hub_user

Nicht implementieren:

AG_DATABASE_URL
AN_DATABASE_URL
HUB_DATABASE_URL

Die bestehende verwaltete Datenbankverbindung bleibt erhalten.


10. OPTIONAL RLS NICHT ALS HAUPTLÖSUNG EINFÜHREN

PostgreSQL Row Level Security ist für diesen Auftrag nicht erforderlich.

Nur verwenden, wenn sie bereits sauber vorhanden ist.

Die maßgebliche Sicherheitsgrenze bleibt:

Application-Level Authorization + currentOrgId/ownerOrgId.


11. PFLICHTTEST

AG Context versucht AN-owned private Row zu lesen:

→ nicht sichtbar / 403 / 404 gemäß bestehender API-Konvention.


12. PFLICHTTEST

AN Context versucht AG-owned private Row zu lesen:

→ nicht sichtbar.


ERGEBNIS

Eine Datenbank bleibt bestehen.

Die organisatorische Trennung erfolgt ausschließlich logisch auf Anwendungsebene.
