SCHRITT 8 – TESTSUITE AUF ECHTE PRODUKTIONSPFADE AUSRICHTEN UND REGRESSIONEN VOLLSTÄNDIG ABSICHERN

ZIEL

Die Test-Suite muss die tatsächlichen Serviceketten prüfen.

Isolierte Helper-Tests allein reichen nicht.

Alte fachlich falsche Erwartungen müssen entfernt werden.

Keine Tests dürfen Fehler durch falsche Mocks oder veraltete Annahmen kaschieren.


1. VERALTETEN CHANGE-PROPOSAL-TEST ENTFERNEN/KORRIGIEREN

Ein Test, der erwartet:

kein Agreement
→ Change Proposal
→ daraus entsteht initiales Agreement

ist fachlich ungültig.

Neue Erwartung:

kein Agreement
→ Change Proposal create
→ 422 CHANGE_PROPOSAL_REQUIRES_AGREEMENT


2. KEIN acceptedProposal ALS AGREEMENT-QUELLE IM TEST

Tests dürfen nicht mehr absichern:

accepted Proposal resolvedAt
→ AGREEMENT_REACHED

Das ist fachlich falsch.


3. TIMELINE-TEST EXAKT AUF ZEITPUNKTE PRÜFEN

Nicht nur Eventanzahl.

Setup:

decisionAt:
05.08.

accepted Change Proposal:
20.08.

Assertions:

AGREEMENT_REACHED.at === 05.08.

CHANGE_PROPOSAL_ACCEPTED.at === 20.08.


4. SCHEDULE-CHANGE TEST ÜBER PRODUKTIVEN ACCEPT-PFAD

Nicht nur:

shiftRequirementsToWindow(...)

testen.

Mindestens ein Integrationstest:

create/open Proposal
→ accept
→ DB prüfen


5. DOUBLE-SHIFT INTEGRATIONSTEST

Zwei aufeinanderfolgende accepted Changes durchführen.

Danach prüfen:

Agreement
Requirements
Bookings

und die tatsächlich an Availability übergebenen Tage.


6. ROLLBACK-TEST

Availability Conflict erzwingen.

Nach 409 prüfen:

Proposal OPEN
Agreement unverändert
Plan unverändert
Versionanzahl unverändert
Requirements unverändert
Bookings unverändert


7. bookingRequirements INITIAL ACCEPTANCE

Availability-Daten so vorbereiten, dass:

availableResources

und:

bookingRequirements

unterschiedliche Booking-Ergebnisse erzeugen würden.

Dann echten Decision-Pfad ausführen.

Assertions auf DB-Bookings müssen beweisen:

bookingRequirements wurden verwendet.


8. CHANGE ACCEPTANCE BOOKING TEST

Gleiche Prüfung für Schedule Change.


9. CONCRETE RESOURCE PRESERVATION

Kompletten Schedule-Change-Pfad.

Alte resourceId = X.

X im neuen Zeitraum verfügbar.

Nach Acceptance:

resourceId = X.


10. CONCRETE RESOURCE CONFLICT

X im neuen Zeitraum durch Fremdbooking blockiert.

Erwartung:

409

kein stiller Fallback auf Type-Level.


11. RESTBEDARF TEST

12. MULTI-CONCRETE TEST

alle vier erhalten.


13. LEGACY NO-REQUIREMENTS TEST

Bestehendes Booking.

Booking noch vorhanden und korrekt verschoben.


14. QUALIFICATION DOUBLE COUNT TEST

nicht FEASIBLE.


15. LEGACY DAILY AVAILABILITY TEST

47. BESTEHENDE SKIPS PRÜFEN

Falls vorhandene relevante Tests bereits geskippt sind:

48. MOCKS NICHT FACHLICH FALSCH MACHEN

Mocks sollen DTOs abbilden, nicht neue State-Logik erfinden.

Bevorzugt zentrale Helper direkt testen.


49. DB-TESTS NACH MÖGLICHKEIT TRANSAKTIONAL ISOLIEREN

Bestehendes Testsetup weiterverwenden.

Keine gegenseitige Abhängigkeit der Testreihenfolge.


50. TESTNAMEN FACHLICH KLAR

Beispiel:

"keeps initial agreement timestamp after later accepted change proposal"

statt generisch:

"timeline works"


51. ABSCHLUSSKONTROLLE

NO_ACTION
