Arbeite auf Basis des aktuellen Repository-Stands.

Dieser Auftrag dient ausschließlich der Behebung der aktuell festgestellten **fachlichen Fehler, inkonsistenten Doppelimplementierungen und technischen Inkonsistenzen**.

Die große zuletzt beschriebene Überarbeitung der Leistungsanfragen-UI noch **nicht** implementieren.

---

# 0. Verbindliche Grundregeln

Keine neuen Features außerhalb dieses Auftrags.

Insbesondere jetzt noch nicht:

```text
kein neues Detailseiten-Design

keine neue Gantt-Funktion
keine neue Resource-Capacity-Übersicht
keine neue EDC-Implementierung
keine Workflow Engine

keine vollständige Legacy-Migration
```

---

# 2. Vor Acceptance neue Ressourcenverfügbarkeit prüfen

Vor jeder Änderung von:

```text
agreedStart
agreedEnd
Plantermin
ResourceBookings
```

müssen die ResourceRequirements für den neuen Zeitraum bestimmt werden.

Dafür vorhandenen Helper verwenden:

```ts
shiftRequirementsToWindow(...)
```

Eingaben:

```text
originalAgreementStart
newAgreementStart
ResourceRequirements
```

Ergebnis:

Requirements mit auf den neuen Termin verschobenen:

```text
periodStart
periodEnd
```

---

# 3. Verschobene Requirements gegen aktuelle Ressourcenlage prüfen

Danach:

```ts
evaluateResourceRequirements(...)
```

mit den verschobenen Requirements ausführen.

Wichtig:

Die bereits aus diesem Service Request stammenden alten `CONFIRMED` Bookings dürfen bei dieser Re-Evaluation nicht als Fremdbelegung gegen den Request selbst gerechnet werden.

Dafür bestehenden Exclude-/Ignore-Mechanismus verwenden oder minimal erweitern:

```ts
excludeSourceReferenceId?: string
```

bzw. vorhandene passende Möglichkeit.

Nicht sämtliche Bookings des AN ignorieren.

Nur die Bookings dieses konkreten Service Requests.

---

# 4. Acceptance bei fehlender Verfügbarkeit abbrechen

Wenn der neue Zeitraum nicht vollständig machbar ist:

```text
keine Änderung am Agreement
keine Änderung am Plan
keine Änderung an Bookings
Proposal bleibt OPEN
```

API-Fehler:

```text
409 CHANGE_PROPOSAL_NOT_FEASIBLE
```

Response nach Möglichkeit:

```ts
{
  code: "CHANGE_PROPOSAL_NOT_FEASIBLE",
  availability: ...
}
```

Keine Teiländerung durchführen.

---

# 5. Alle Änderungen in einer DB-Transaktion

Folgende Änderungen atomar:

```text
1. Availability erfolgreich geprüft
2. Plan/Leistung aktualisieren
3. neue Leistungsversion erzeugen
4. Agreement aktualisieren
5. relevante ResourceBookings ersetzen
6. Proposal auf ACCEPTED setzen
```

Wenn ein Schritt fehlschlägt:

```text
ROLLBACK
```

---

# 6. Bestehende Bookings nicht nur per Millisekunden-Offset verschieben

Aktuell vorhandene Logik wie:

```ts
deltaMs = newStart - oldStart
booking.start += deltaMs
booking.end += deltaMs
```

für Service-Request-Bookings entfernen.

Grund:

Sie ist falsch bei:

```text
geänderter Dauer
unterschiedlichen Requirement-Teilzeiträumen
abweichenden Uhrzeiten
Sommer-/Winterzeit
```

---

# 7. Bookings aus verschobenen Requirements neu erzeugen

Für automatisch aus dem Service Request stammende Bookings:

```text
alte fachbezogene Auto-Bookings dieses Requests identifizieren
```

nur über:

```text
sourceType
sourceReferenceId
```

Keine manuellen Bookings anfassen.

Danach aus den verschobenen Requirements neue Booking-Spezifikationen bilden.

Pro Requirement mindestens erhalten:

```ts
{
  resourceTypeId,
  quantity,
  utilizationPercent,
  periodStart,
  periodEnd,
  requiredQualification
}
```

Keine Zusammenfassung unterschiedlicher Requirement-Zeiträume in einen einzigen Booking-Eintrag.

---

# 8. Konkrete Resource-Zuordnung erhalten, wenn möglich

Wenn ein bestehendes automatisches Booking eine konkrete:

```text
resourceId
```

enthält und diese Ressource im neuen Zeitraum weiterhin verfügbar ist:

```text
resourceId beibehalten
```

Wenn sie nicht verfügbar ist:

```text
nicht automatisch irgendeine andere konkrete Resource auswählen
```

Für den PoC bevorzugt:

```text
Acceptance mit Konflikt abbrechen
```

oder vorhandene Type-Level-Booking-Logik verwenden, wenn dies bereits der etablierte Workflow ist.

Keine neue automatische Optimierung bauen.

---

# 9. Type-Level-Bookings korrekt neu erzeugen

Bei:

```text
resourceId = null
resourceTypeId != null
```

müssen erhalten bleiben:

```text
resourceTypeId
quantity
utilizationPercent
periodStart
periodEnd
```

`quantity` nicht aus verschiedenen Requirements addieren, wenn deren Zeiträume unterschiedlich sind.

---

# 10. Leistungsversion korrekt erzeugen

Aktuell darf nicht nur:

```text
leistung.version++
```

erfolgen.

Wenn das bestehende Modell Leistungsversionen speichert:

```text
neue Version über denselben bestehenden Versionierungsmechanismus erzeugen
```

Verknüpfung möglichst dokumentieren:

```text

```

nur falls bestehendes Versionsmodell ein entsprechendes Metadata-/Reason-Feld besitzt.

Kein großes neues Versionsmodell schaffen.

# 19. Überlappende Qualifikationen konservativ behandeln

Problem:

Eine konkrete Resource kann mehrere Qualifikationen besitzen und dadurch bei zwei Qualification-Gruppen doppelt als verfügbare Kapazität erscheinen.

Für diesen PoC keine komplexe Matching-/Optimierungs-Engine bauen.

Implementiere stattdessen eine konservative Regel:

Wenn mehrere gleichzeitig aktive Requirements:

```text
gleichen ResourceType
aber unterschiedliche requiredQualification
```

haben und dieselben konkreten Resources mehrere dieser Qualifikationen erfüllen können:

```text
dieselbe konkrete Resource darf bei der aggregierten Tageskapazität nicht mehrfach gezählt werden
```

Mindestens testbar sicherstellen:

```text
6 reale Personen
4 benötigt mit Qualification A
4 benötigt mit Qualification B

wenn alle 6 Personen A und B haben
→ Ergebnis darf nicht 8 verfügbare Personen vortäuschen
```

Wenn eine vollständige optimale Zuordnung zu komplex wäre:

```text
konservativ Konflikt melden
```

statt Machbarkeit fälschlich zu bestätigen.
