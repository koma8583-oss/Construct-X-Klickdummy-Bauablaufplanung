SCHRITT 1 – PROJEKTMITGLIEDSCHAFT ALS EIGENEN FACHLICHEN LIFECYCLE MODELLIEREN

ZIEL

Die bisherige direkte Zuordnung eines AN zu einem Projekt soll durch eine bilateral bestätigte Projektmitgliedschaft ersetzt werden.

Der AG darf einen AN künftig nur EINLADEN.

Erst die ausdrückliche Zustimmung des AN darf die Projektbeziehung auf ACTIVE setzen.

Der fachliche Ablauf muss lauten:

Datenraumteilnehmer
→ PROJECT_INVITATION
→ INVITED
→ AN nimmt an
→ ACTIVE
→ erst danach Leistungszuordnung

Alternativ:

INVITED
→ AN lehnt ab
→ REJECTED

Später:

ACTIVE
→ Projektbeziehung beenden
→ REVOKED


1. BESTEHENDE STRUKTUREN ZUERST ANALYSIEREN

Prüfe insbesondere:

- project_contractors
- project_subcontractors, falls vorhanden
- /projects/:projectId/contractors
- /ag/projects/:projectId/subcontractors
- alle Services, die Projekt-AN-Zuordnungen erzeugen
- alle Stellen, die assignmentStatus === ACTIVE prüfen
- Leistungsanfrage-Erstellung
- Data Publication
- AG-Projektansichten
- AN-Projektansichten

Ziel ist ausdrücklich NICHT, einen dritten parallelen Zuordnungsmechanismus zu erzeugen.

Die bisher zwei überlappenden AG-Zuordnungswege müssen am Ende fachlich konsolidiert sein.


2. BEVORZUGTES ZIELMODELL

Eine eigene Tabelle verwenden:

project_memberships

oder, falls Naming im Projekt anders gehandhabt wird:

project_participants

Bevorzugt:

project_memberships


3. SCHEMA

Mindestens:

id

projectId

agOrgId
anOrgId

anParticipantId

status

invitationMessage nullable

invitedAt
respondedAt nullable
acceptedAt nullable
rejectedAt nullable
revokedAt nullable

createdAt
updatedAt

Optional, falls bereits benötigt:

invitationExpiresAt
remoteInvitationId
dataspaceCorrelationId


4. STATUS-ENUM

Neues eindeutiges Enum:

INVITED
ACTIVE
REJECTED
REVOKED

Optional nur wenn wirklich verwendet:

EXPIRED

Nicht für Project Membership verwenden:

PLANNED
COMPLETED

Diese Begriffe gehören eher zur Leistung oder Ausführung, nicht zur Zustimmung eines Unternehmens zu einer Projektbeziehung.


5. UNIQUE CONSTRAINT

Pro Projekt und AN darf nur eine aktuelle fachliche Mitgliedschaft existieren.

Bevorzugt:

UNIQUE(projectId, anOrgId)

Falls ein späteres Re-Invite nach REJECTED/REVOKED als neue Row benötigt wird:

stattdessen gezielt entscheiden, ob:

A) dieselbe Membership reaktiviert wird

oder

B) separate Invitation-History geführt wird.

Für den PoC bevorzugt:

eine Membership Row pro projectId + anOrgId

plus Audit-/Message-Historie separat.


6. KEINE GEWERKE ODER ARBEITSPAKETE IN DIE MITGLIEDSCHAFT MISCHEN

Project Membership beantwortet nur:

„Darf diese Organisation an diesem Projekt als Projektpartner teilnehmen?“

Nicht:

„Welche Leistung übernimmt sie?“

Deshalb nicht als Pflichtbestandteil der Membership speichern:

- Gewerk
- Arbeitspaket
- Takt
- konkrete Leistung
- Ressourcenbedarf

Diese Informationen gehören später zur Leistungsanfrage bzw. Leistungszuordnung.


7. ACTIVE DARF NICHT BEIM CREATE GESETZT WERDEN

Jeder neue AG-initiierte Beitrittsprozess startet ausschließlich mit:

status = INVITED

Backendseitig erzwingen.

Ein Request Body wie:

{
  "status": "ACTIVE"
}

vom AG darf nicht funktionieren.


8. STATUS-TRANSITIONEN ZENTRAL DEFINIEREN

Erlaubt:

INVITED → ACTIVE
nur durch AN

INVITED → REJECTED
nur durch AN

INVITED → REVOKED
durch AG, wenn Einladung zurückgezogen wird

ACTIVE → REVOKED
entsprechend bestehender fachlicher Rechte

Nicht erlaubt:

REJECTED → ACTIVE
ohne neuen expliziten Invite-Prozess

REVOKED → ACTIVE
ohne neuen expliziten Invite-Prozess


9. KEINE DIREKTEN STATUS-UPDATES AUS ROUTEN

Nicht:

route
→ UPDATE project_memberships SET status = ...

Stattdessen zentraler Service:

ProjectMembershipService

mit:

invite(...)
accept(...)
reject(...)
revoke(...)


10. BESTEHENDE project_contractors DATEN MIGRIEREN

Nicht blind löschen.

Bestehende ACTIVE-Zuordnungen gelten als Legacy-Projektpartner.

Migration:

bestehende aktive project_contractors
→ project_memberships ACTIVE

acceptedAt kann bei Legacy ggf. null bleiben.

Nicht künstlich behaupten, der AN habe historisch zugestimmt, wenn das nicht gespeichert wurde.


11. BESTEHENDE ABHÄNGIGKEITEN AUF ACTIVE UMSTELLEN

Alle Funktionen, die bisher prüfen:

project_contractors.assignmentStatus === ACTIVE

müssen künftig die zentrale Project Membership prüfen:

project_memberships.status === ACTIVE


12. PFLICHTTESTS

TEST A

AG lädt AN ein.

Erwartung:

status = INVITED

Nicht ACTIVE.


TEST B

AG versucht beim Create direkt ACTIVE zu setzen.

Erwartung:

nicht möglich.


TEST C

AN akzeptiert INVITED.

Erwartung:

ACTIVE
acceptedAt gesetzt.


TEST D

AN lehnt ab.

Erwartung:

REJECTED
rejectedAt gesetzt.


TEST E

anderer AN versucht fremde Einladung anzunehmen.

Erwartung:

403.


TEST F

AG versucht INVITED → ACTIVE direkt.

Erwartung:

403 oder fachlich geeigneter Fehler.


13. ABSCHLUSSKONTROLLE

Global suchen nach:

project_contractors
assignmentStatus
ACTIVE
subcontractors

Prüfen, welche alten Pfade die Zustimmung des AN noch umgehen könnten.

Nach diesem Schritt muss klar sein:

Projektmitgliedschaft und Leistungszuordnung sind zwei getrennte fachliche Konzepte.

SCHRITT 2 – AN-AUSWAHL AUF DATENRAUMTEILNEHMER UND PARTICIPANT DISCOVERY UMRÜSTEN

ZIEL

Der AG soll beim Einladen nicht mehr einfach alle lokal gespeicherten Organisationen vom Typ AN sehen.

Die Liste soll konzeptionell die AN repräsentieren, die eine gültige Datenraumidentität besitzen und für eine Datenraumkommunikation erreichbar sind.

Der PoC darf dafür weiterhin eine lokale Registry verwenden.

Die Fachanwendung soll aber bereits gegen eine saubere Datenraum-Abstraktion programmieren.


1. BESTEHENDEN RESOLVER PRÜFEN

Insbesondere vorhandene Funktion:

resolveDataspaceParticipant(...)

oder aktuellen äquivalenten Service prüfen.

Wenn aktuell nur:

{
  localOrgId
}

zurückgegeben wird, obwohl der Typ bereits:

participantId
connectorEndpoint

vorsieht:

den bestehenden Mechanismus erweitern.

Keine zweite parallele Discovery-Implementierung daneben bauen.


2. ZENTRALES INTERFACE DEFINIEREN

Bevorzugt:

interface ParticipantDirectory {
  listParticipants(
    filter?: ParticipantFilter
  ): Promise<DataspaceParticipant[]>;

  resolveParticipant(
    participantId: string
  ): Promise<DataspaceParticipant | null>;
}

Optional:

resolveByLocalOrganizationId(...)


3. DTO

DataspaceParticipant mindestens:

{
  participantId: string;

  localOrgId?: string;

  organizationName: string;

  organizationType: "AG" | "AN";

  identityStatus:
    | "VERIFIED"
    | "UNVERIFIED"
    | "SUSPENDED";

  connectorEndpoint?: string;

  connectorStatus:
    | "AVAILABLE"
    | "UNAVAILABLE"
    | "UNKNOWN";

  capabilities?: string[];
}


4. PO C IMPLEMENTIERUNG

Für den aktuellen PoC eine:

LocalParticipantDirectory

verwenden.

Daten können weiterhin aus PostgreSQL stammen.

Beispielsweise Tabelle:

dataspace_participants

mit:

participantId
localOrgId nullable
organizationName
organizationType
identityStatus
connectorEndpoint
connectorStatus
capabilities JSON
updatedAt


5. KEINE ABHÄNGIGKEIT VON localOrgId ERZWINGEN

Ein Datenraumteilnehmer kann perspektivisch bekannt sein, bevor eine vollständige lokale Organisation angelegt wurde.

Deshalb:

participantId

ist die Datenraumkennung.

localOrgId ist eine lokale Mapping-Information.


6. AG-LISTE

Neuer API-Pfad beispielsweise:

GET /api/dataspace/participants?organizationType=AN

oder passend zur bestehenden Routingstruktur.

Nur anzeigen:

organizationType = AN
identityStatus = VERIFIED

Optional:

connectorStatus berücksichtigen.


7. BEREITS AKTIVE ODER EINGELADENE AN MARKIEREN

Antwort sinnvoll ergänzen um projektbezogenen Zustand:

membershipStatus:

null
INVITED
ACTIVE
REJECTED
REVOKED

oder diese Information in der AG-UI aus Memberships mappen.


8. AUSWAHLLOGIK

AG darf einen AN auswählen, wenn:

identityStatus === VERIFIED

und kein:

INVITED
ACTIVE

für dieses Projekt besteht.

REJECTED/REVOKED:
je nach gewünschter Re-Invite-Regel erneut einladbar.


9. KEINE LEISTUNGSDATEN BEI PARTICIPANT DISCOVERY

Participant Directory liefert keine:

- Takte
- Ressourcen
- Arbeitspakete
- internen Projekte
- Bookings

Nur Teilnehmer-/Discoveryinformationen.


10. CONNECTOR DISCOVERY

Beim Einladen muss aus:

participantId

der technische Endpoint ermittelbar sein.

Beispiel:

resolveParticipant("AN-4711")

→

{
  participantId: "AN-4711",
  connectorEndpoint: "https://..."
}


11. FEHLERFALL

Participant ist zwar auswählbar, Connector aber zum Versandzeitpunkt nicht auflösbar:

Einladung NICHT als erfolgreich versendet behandeln.

Membership kann fachlich INVITED bleiben, während der technische Message-Status FAILED ist.

Fachlichen Membership-Status und technischen Transportstatus nicht vermischen.


12. SPÄTERE MIGRATION

Die Fachanwendung soll nur:

ParticipantDirectory

kennen.

Später kann implementiert werden:

FederatedParticipantDirectory
ConstructXParticipantDirectory
EDCDiscoveryAdapter

ohne AG-UI oder ProjectMembershipService neu schreiben zu müssen.


13. PFLICHTTESTS

- VERIFIED AN erscheint.
- UNVERIFIED AN erscheint nicht.
- AG erscheint nicht in AN-Auswahl.
- ACTIVE AN wird als bereits Projektpartner markiert.
- INVITED AN kann nicht doppelt eingeladen werden.
- participantId wird korrekt zum Connector Endpoint aufgelöst.


14. ABSCHLUSSKONTROLLE

Global prüfen:

GET /organizations?type=AN

darf nicht mehr die primäre Quelle für:

„AN zum Projekt einladen“

sein.

Lokale Organisationsdaten dürfen nur noch für lokale Mappings bzw. Anzeigen dienen.

SCHRITT 3 – PROJECT_INVITATION UND PROJECT_INVITATION_RESPONSE ÜBER DataspaceExchange IMPLEMENTIEREN

ZIEL

Die Projekteinladung und die Antwort des AN müssen als echte organisationsübergreifende Datenraumkommunikation behandelt werden.

Sie dürfen nicht nur durch gemeinsame Datenbankänderungen simuliert werden.

Der fachliche Kommunikationsfluss lautet:

AG
→ PROJECT_INVITATION
→ AN

AN
→ PROJECT_INVITATION_RESPONSE
→ AG


1. DataspaceExchange ERWEITERN

Vorhandenes Interface prüfen.

Zusätzlich zu:

publishServiceRequest(...)
publishServiceResponse(...)

einführen:

publishProjectInvitation(...)
publishProjectInvitationResponse(...)

und auf Inbound-Seite:

receiveProjectInvitation(...)
receiveProjectInvitationResponse(...)


2. KEINE GENERISCHE any-NACHRICHT

Eigene DTOs definieren:

ExternalProjectInvitation

ExternalProjectInvitationResponse


3. ExternalProjectInvitation

Empfohlen:

{
  metadata: {
    messageId: string;
    correlationId: string;
    schemaVersion: "1.0";
    createdAt: string;

    senderParticipantId: string;
    recipientParticipantId: string;
  };

  project: {
    projectReference: string;
    projectName: string;
    description?: string;
    location?: string;
  };

  requestedRole: "CONTRACTOR";

  purpose: "PROJECT_COLLABORATION";

  invitationMessage?: string;

  validUntil?: string;

  policy: {
    usagePurpose: "PROJECT_MEMBERSHIP";
    allowedConsumerParticipantId: string;
  };
}


4. KEINE LEISTUNG IM INVITATION PAYLOAD

Nicht enthalten:

- Service Request
- Takt
- konkrete Leistungs-ID
- Resource Requirements
- interne Gesamtplanung
- andere Projektpartner
- interne Ressourceninformationen

Projekt-Einladung und Leistungsanfrage bleiben strikt getrennt.


5. RESPONSE DTO

ExternalProjectInvitationResponse:

{
  metadata: {
    messageId: string;
    correlationId: string;
    schemaVersion: "1.0";
    createdAt: string;

    senderParticipantId: string;
    recipientParticipantId: string;
  };

  invitationId: string;

  projectReference: string;

  decision:
    | "ACCEPTED"
    | "REJECTED";

  message?: string;

  respondedAt: string;
}


6. correlationId

Einladung und Antwort müssen dieselbe fachliche Korrelation besitzen.

Beispiel:

project-membership:{projectId}:{participantId}:{invitationId}


7. OUTBOUND POLICY

Für Project Invitation eigenen Purpose verwenden:

PROJECT_MEMBERSHIP

Nicht einfach:

CONSTRUCTION_COORDINATION

verwenden.

Der zweite Purpose beginnt erst nach ACTIVE Membership.


8. POLICY FÜR INVITATION

Mindestens:

sender = AG Participant

receiver = gewählter AN Participant

purpose = PROJECT_MEMBERSHIP

messageType = PROJECT_INVITATION

optional:
validUntil


9. RESPONSE POLICY

Antwort ausschließlich zurück an den ursprünglichen AG.

messageType:

PROJECT_INVITATION_RESPONSE


10. OUTBOX / AUDIT

Bestehende Outbox-/Audit-Infrastruktur verwenden.

Nicht neue unabhängige Message-History bauen.

Speichern:

messageId
correlationId
type
senderParticipantId
receiverParticipantId
status
createdAt
sentAt
deliveredAt, falls vorhanden
error


11. INBOUND IDEMPOTENZ

Gleiche:

messageId

darf nur einmal fachlich verarbeitet werden.

Bestehende Dataspace-Inbound-Idempotenz wiederverwenden.


12. INBOUND PROJECT_INVITATION

Processor:

processIncomingProjectInvitation(...)

muss auf AN-Seite:

- Senderidentität prüfen
- Recipient Participant prüfen
- Payload validieren
- Projektinformationen lokal anlegen/referenzieren
- Invitation/Membership als INVITED speichern
- NICHT ACTIVE setzen


13. INBOUND RESPONSE

processIncomingProjectInvitationResponse(...)

auf AG-Seite:

ACCEPTED
→ INVITED → ACTIVE

REJECTED
→ INVITED → REJECTED


14. STATUS NUR BEI KORREKTER KORRELATION ÄNDERN

Response muss passen zu:

- invitationId
- correlationId
- projectReference
- erwarteter AN Participant
- erwarteter AG Participant

Sonst:
keine Statusänderung.


15. KEIN SHARED-DB-SHORTCUT

Auch wenn AG und AN im PoC dieselbe PostgreSQL-Instanz nutzen:

fachliche organisationsübergreifende Änderung muss über DataspaceExchange laufen.

Nicht ausschließlich:

AG INSERT
→ AN sieht dieselbe gemeinsame Row

als Datenraumsimulation verwenden.


16. PFLICHTTEST – INVITATION OUTBOUND

AG lädt AN ein.

Erwartung:

PROJECT_INVITATION Message erzeugt.

Membership:
INVITED.


17. PFLICHTTEST – ACCEPT RESPONSE

AN akzeptiert.

PROJECT_INVITATION_RESPONSE:
ACCEPTED

AG Membership:
ACTIVE.


18. PFLICHTTEST – REJECT

AN lehnt ab.

AG Membership:
REJECTED.


19. PFLICHTTEST – DUPLICATE

gleiche PROJECT_INVITATION messageId zweimal inbound.

Nur eine fachliche Einladung.


20. PFLICHTTEST – FALSCHE RESPONSE

anderer Participant antwortet.

Keine Statusänderung.

403/422 entsprechend vorhandener Security-/Validation-Logik.

SCHRITT 4 – ZENTRALEN ProjectMembershipService UND EINDEUTIGE API IMPLEMENTIEREN

ZIEL

Alle fachlichen Operationen rund um Projekteinladungen und Projektmitgliedschaften sollen über einen einzigen zentralen Service laufen.

Die bisher parallelen Contractor-/Subcontractor-Zuordnungswege dürfen die Zustimmung nicht mehr umgehen.


1. CENTRAL SERVICE

Bevorzugt:

project-membership-service.ts

mit mindestens:

listProjectMemberships(...)

inviteParticipant(...)

acceptInvitation(...)

rejectInvitation(...)

revokeMembership(...)

getMembership(...)

listPendingInvitations(...)


2. inviteParticipant(...)

Input:

projectId
agOrgId/currentOrg
participantId
optional invitationMessage
optional validUntil


3. inviteParticipant VALIDIERUNGEN

Prüfen:

- Projekt existiert.
- aktueller AG darf Projekt verwalten.
- Participant existiert.
- Participant ist Typ AN.
- identityStatus = VERIFIED.
- AG kann sich nicht selbst einladen.
- keine INVITED Membership vorhanden.
- keine ACTIVE Membership vorhanden.


4. INVITATION TRANSACTION

Bevorzugter Ablauf:

1. Membership INVITED erzeugen.
2. invitationId/correlationId erzeugen.
3. Outbox Message in derselben Transaktion erzeugen.
4. Commit.
5. Outbox sendet anschließend über DataspaceExchange.

Nicht:

Remote Send
→ danach erst lokale DB schreiben

sonst kann ein Remotezustand ohne lokale Nachvollziehbarkeit entstehen.


5. TRANSPORTFEHLER

Wenn Versand scheitert:

Membership bleibt:

INVITED

aber technischer Message Status:

FAILED

AG UI zeigt beispielsweise:

„Einladung konnte nicht übertragen werden.“

[Erneut senden]

Kein automatischer Wechsel zu REJECTED.


6. ACCEPT

AN darf nur eine an ihn gerichtete Einladung annehmen.

Validieren:

membership.status === INVITED

recipientParticipantId entspricht aktuellem AN.


7. ACCEPT CONCURRENCY

UPDATE ...

WHERE id = ?
AND status = 'INVITED'

SET
status = 'ACTIVE',
acceptedAt = ...

RETURNING *

Wenn keine Row:

409 PROJECT_INVITATION_ALREADY_RESOLVED


8. REJECT

Gleicher Mechanismus:

INVITED → REJECTED

respondedAt setzen.

rejectedAt setzen.


9. REVOKE

Zwei Fälle:

INVITED:
AG zieht Einladung zurück.

ACTIVE:
Projektbeziehung wird beendet.

Status:

REVOKED


10. BESTEHENDE LEISTUNGEN BEI REVOKE

Keine bestehende Leistung still löschen.

Wenn ACTIVE Membership bereits aktive Leistungsanfragen/Agreements besitzt:

für den PoC bevorzugt:

409 PROJECT_MEMBERSHIP_HAS_ACTIVE_SERVICES

Keine automatische Löschung oder Terminänderung.


11. ROUTES

Empfohlen, angepasst an vorhandene API-Konvention:

GET
/projects/:projectId/memberships

POST
/projects/:projectId/invitations

GET
/project-invitations

POST
/project-invitations/:id/accept

POST
/project-invitations/:id/reject

POST
/project-memberships/:id/revoke


12. KEIN GENERISCHES status PATCH

Nicht:

PATCH membership

{
  "status": "ACTIVE"
}

Das würde den Lifecycle umgehen.


13. ALTE ROUTES KONSOLIDIEREN

Prüfen:

POST /projects/:projectId/contractors

POST /ag/projects/:projectId/subcontractors

Diese dürfen nicht weiterhin direkt ACTIVE-Zuordnungen erzeugen.


14. BEVORZUGTE MIGRATION

Alte UI auf neue Invitations API umstellen.

Alte Create-Routes anschließend:

A) entfernen

oder

B) temporär auf inviteParticipant(...) delegieren.

Unter keinen Umständen direkt ACTIVE schreiben.


15. RESPONSE CODES

Invite Success:
201

Duplicate INVITED:
409

bereits ACTIVE:
409

Participant nicht verfügbar/verifiziert:
422 oder bestehende fachlich passende API-Semantik

Unauthorized:
403

Already resolved:
409


16. DOMAIN ERROR CODES

Beispielsweise:

PROJECT_INVITATION_ALREADY_EXISTS

PROJECT_MEMBERSHIP_ALREADY_ACTIVE

PROJECT_INVITATION_NOT_FOUND

PROJECT_INVITATION_ALREADY_RESOLVED

PROJECT_PARTICIPANT_NOT_VERIFIED

PROJECT_PARTICIPANT_NOT_REACHABLE

PROJECT_MEMBERSHIP_HAS_ACTIVE_SERVICES

PROJECT_MEMBERSHIP_NOT_ACTIVE


17. PFLICHTTESTS

- Invite erzeugt INVITED.
- Duplicate Invite → 409.
- ACTIVE Partner erneut einladen → 409.
- AN Accept → ACTIVE.
- AN Reject → REJECTED.
- AG kann Accept nicht ausführen.
- fremder AN kann Accept nicht ausführen.
- paralleles Accept/Reject → genau eine Resolution.
- Legacy Create Route kann nicht direkt ACTIVE erzeugen.
