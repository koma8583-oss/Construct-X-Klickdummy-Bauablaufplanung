# Aufgabe 2.2 – Getrennte Statusmodelle definieren

Ergänze die fachlichen Statusmodelle für Takte und Taktanfragen.

Bearbeite:

* die OpenAPI-Spezifikation
* die zentrale Domain- oder Typdefinition
* eine neue Dokumentationsdatei `docs/state-model.md`

Ändere noch keine Datenbanktabellen und keine API-Endpunkte.

## Ziel

Der Zustand eines Takts muss vom Zustand einer einzelnen Taktanfrage getrennt werden.

Ein technisch zugestellter oder fachlich abgelehnter Request darf nicht automatisch den gesamten Takt auf zugestellt oder abgelehnt setzen.

## Neues Enum `TaktLifecycleStatus`

Definiere folgende Werte:

```text
DRAFT
PLANNED
IN_COORDINATION
CONFIRMED
CANCELLED
```

Bedeutung:

* `DRAFT` – Takt wird bearbeitet.
* `PLANNED` – Takt ist planungsseitig vorbereitet.
* `IN_COORDINATION` – mindestens eine Abstimmung mit einem Nachunternehmer läuft.
* `CONFIRMED` – die Ausführung wurde fachlich bestätigt.
* `CANCELLED` – der Takt wurde aufgehoben.

## Neues Enum `TaktRequestStatus`

Definiere folgende Werte:

```text
DRAFT
SENT
DELIVERED
DETAILS_RETRIEVED
UNDER_REVIEW
ACCEPTED
ALTERNATIVES_PROPOSED
REJECTED
REVISION_REQUIRED
CANCELLED
EXPIRED
SUPERSEDED
```

## Dokumentiere zulässige Übergänge

Mindestens folgende Übergänge sollen zulässig sein:

```text
DRAFT → SENT
DRAFT → CANCELLED

SENT → DELIVERED
SENT → CANCELLED
SENT → EXPIRED

DELIVERED → DETAILS_RETRIEVED
DELIVERED → UNDER_REVIEW
DELIVERED → CANCELLED
DELIVERED → EXPIRED

DETAILS_RETRIEVED → UNDER_REVIEW
DETAILS_RETRIEVED → ACCEPTED
DETAILS_RETRIEVED → ALTERNATIVES_PROPOSED
DETAILS_RETRIEVED → REJECTED
DETAILS_RETRIEVED → CANCELLED
DETAILS_RETRIEVED → EXPIRED

UNDER_REVIEW → ACCEPTED
UNDER_REVIEW → ALTERNATIVES_PROPOSED
UNDER_REVIEW → REJECTED
UNDER_REVIEW → CANCELLED
UNDER_REVIEW → EXPIRED

ALTERNATIVES_PROPOSED → ACCEPTED
ALTERNATIVES_PROPOSED → REVISION_REQUIRED
ALTERNATIVES_PROPOSED → SUPERSEDED

REJECTED → REVISION_REQUIRED
REJECTED → SUPERSEDED

REVISION_REQUIRED → SUPERSEDED
```

Folgende Zustände sind grundsätzlich terminal:

```text
ACCEPTED
CANCELLED
EXPIRED
SUPERSEDED
```

## Fachliche Regeln

Dokumentiere ausdrücklich:

* `DELIVERED` ist nur ein technischer Zustand.
* `ACCEPTED` ist eine fachliche Entscheidung.
* `REJECTED` bezieht sich auf eine konkrete Anfrage, nicht automatisch auf den Takt.
* Eine abgelehnte Alternative führt zu `REVISION_REQUIRED`.
* Eine neue Anfrageversion setzt die alte Anfrage auf `SUPERSEDED`.
* Erst eine akzeptierte Antwort oder Alternative kann den Takt auf `CONFIRMED` setzen.
* Eine offene Anfrage kann den Takt auf `IN_COORDINATION` setzen.
* Der Taktstatus darf nicht direkt aus dem Transportstatus abgeleitet werden.

## Übergangsprüfung

Implementiere eine kleine, frameworkunabhängige Funktion, zum Beispiel:

```ts
isValidTaktRequestTransition(
  currentStatus: TaktRequestStatus,
  nextStatus: TaktRequestStatus
): boolean
```

Optional zusätzlich:

```ts
assertValidTaktRequestTransition(...)
```

Die Funktion darf noch nicht automatisch von bestehenden Delegation-Endpunkten verwendet werden.

## Tests

Ergänze Tests für:

* gültige Übergänge
* ungültige Rücksprünge
* Übergang aus terminalen Zuständen
* Unterschied zwischen `DELIVERED` und `ACCEPTED`

## Einschränkungen

* keine Datenbankänderung
* keine neuen REST-Endpunkte
* keine Änderung bestehender Delegation-Logik
* keine UI-Änderung

## Abschluss

Berichte:

* neu definierte Enums
* Speicherort der Übergangslogik
* dokumentierte Zustandsübergänge
* Testergebnisse
* Ergebnis von Codegenerierung und Typecheck

# Aufgabe 2.4 – Tabellen für Taktanfragen und unveränderliche Snapshots anlegen

## Anforderungen

### Identifikatoren

* Verwende für `id` den bestehenden ID-Typ des Projekts.
* `requestNumber` ist eine fachlich lesbare, eindeutige Referenz.
* `requestNumber` erhält einen Unique Constraint.

### Referenzen

* `taktId` referenziert einen bestehenden Takt.
* `guOrgId` referenziert die GU-Organisation.
* `nuOrgId` referenziert die adressierte NU-Organisation.
* `createdByUserId` referenziert den erstellenden Benutzer.

* `taktVersion` ist nicht nullable.
* `taktVersion` muss mindestens `1` sein.
* Der Wert beschreibt die bei Erstellung der Anfrage verwendete Taktversion.

### Status

* `status` verwendet `TaktRequestStatus`.
* Standardwert ist `DRAFT`.

### Zeitfelder

* `responseRequiredBy` darf zunächst nullable sein, falls bestehende Workflows dies benötigen.
* `sentAt`, `deliveredAt` und `detailsRetrievedAt` sind nullable.
* `createdAt` und `updatedAt` sind nicht nullable.

Ergänze geeignete Indizes mindestens für:

```text

guOrgId
nuOrgId

responseRequiredBy
createdAt
```

Prüfe, ob kombinierte Indizes sinnvoll sind, beispielsweise:

```text
nuOrgId + status
guOrgId + status

```

## Tabelle `takt_request_snapshots`

Ergänze mindestens:

```text
id
taktRequestId
schemaVersion
snapshotPayload
createdAt
```

## Anforderungen an den Snapshot

* `taktRequestId` referenziert `takt_requests`.
* Pro Taktanfrage ist genau ein Snapshot erlaubt.
* Setze einen Unique Constraint auf `taktRequestId`.
* `schemaVersion` ist nicht nullable.
* Standardwert kann `1.0` sein.
* `snapshotPayload` wird als JSON beziehungsweise JSONB gespeichert.
* `snapshotPayload` ist nicht nullable.
* Snapshot-Datensätze sollen nicht aktualisiert werden.
* Snapshot-Datensätze sollen nicht automatisch mit Änderungen am Takt verändert werden.

## Löschverhalten

Wähle ein nachvollziehbares Foreign-Key-Verhalten.

Bevorzugt:

* TaktRequest nicht automatisch löschen, wenn ein Takt gelöscht werden soll.
* Historische Anfragen und Snapshots sollen erhalten bleiben.
* Falls das bestehende System physisches Löschen verwendet, verhindere Datenverlust durch geeignete Restriktionen.

Dokumentiere die Entscheidung.

# Aufgabe 2.6 – Datenzugriffsschicht für Taktanfragen und Antworten implementieren

Implementiere eine interne Datenzugriffs- beziehungsweise Repository-Schicht für die neuen Tabellen.

Es sollen noch keine öffentlichen REST-Endpunkte ergänzt werden.

Nutze die bestehende Architektur und den bestehenden Stil für Datenbankzugriffe.

## Ziel

Die neuen Tabellen sollen nicht direkt aus zukünftigen Routes heraus angesprochen werden müssen.

Implementiere klar abgegrenzte Repository- oder Service-Funktionen.

## Funktionen für `TaktRequest`

```ts

```

Passe Namen und Parameter an den vorhandenen Stil an.

## Funktionen für Snapshots

Mindestens:

```ts

getTaktRequestSnapshot(...)
```

Regeln:

* Pro Anfrage darf nur ein Snapshot erzeugt werden.
* Ein bestehender Snapshot darf nicht überschrieben werden.
* Es darf keine allgemeine Update-Funktion für Snapshots geben.
* Snapshot-Payloads müssen als validierbares Objekt behandelt werden.

## Funktionen für Antworten

Mindestens:

```ts

getTaktResponseByRequestId(...)
getTaktResponseWithAlternatives(...)
```

## Funktionen für Alternativen

Die Alternativen sollen möglichst innerhalb einer Transaktion gemeinsam mit der Antwort gespeichert werden.

Regeln:

* höchstens drei Alternativen
* eindeutige `alternativeId`
* eindeutiger `rank`
* `proposedEnd` liegt nach `proposedStart`
* `crewSize` ist mindestens 1, falls vorhanden

## Validierung der Antwort

Implementiere in der Service-Schicht folgende Regeln:

### `ACCEPTED`

* `acceptedStart` erforderlich
* `acceptedEnd` erforderlich
* `acceptedEnd` nach `acceptedStart`
* keine Alternativen erforderlich

### `ALTERNATIVES_PROPOSED`

* mindestens eine Alternative
* maximal drei Alternativen
* kein angenommenes Zeitfenster erforderlich

### `REJECTED`

* keine Alternative erforderlich
* `reasonCode` empfohlen, aber nicht zwingend, falls bestehendes Schema dies nicht vorsieht

## Statusänderung

`updateTaktRequestStatus` muss die in Aufgabe 2.2 implementierte Übergangsprüfung verwenden.

Ungültige Übergänge müssen einen klaren Domain-Fehler auslösen.

## Organisationsfilter

Vermeide eine Funktion, die ungefiltert alle Anfragen an beliebige Benutzer zurückgibt.

## Tests

# Aufgabe 2.7 – Entwicklungsdaten für neue Taktmodelle ergänzen

Erweitere ausschließlich die vorhandene Seed- beziehungsweise Entwicklungsdatenlogik um Beispieldaten für die neuen Tabellen.

Bestehende Seed-Daten dürfen nicht entfernt werden.

## Ziel

Nach einem Reset beziehungsweise Seed sollen neue Taktanfragen und Antworten für spätere Entwicklungsschritte verfügbar sein.

## Beispieldaten

Erzeuge mindestens folgende Fälle.

### Fall 1 – Offene Taktanfrage

* bestehender Takt
* Taktversion `1`
* GU-Organisation
* adressierte NU-Organisation
* Status `DELIVERED`
* Antwortfrist in der Zukunft
* genau ein TaktRequestSnapshot
* noch keine Antwort

### Fall 2 – Bestätigte Anfrage

* Status `ACCEPTED`
* Antwort mit `decision = ACCEPTED`
* gültiges angenommenes Zeitfenster
* keine Alternativen

### Fall 3 – Anfrage mit Alternativen

* Status `ALTERNATIVES_PROPOSED`
* Antwort mit `decision = ALTERNATIVES_PROPOSED`
* zwei Alternativen
* unterschiedliche Zeitfenster
* eindeutige Rangfolge
* generischer `reasonCode = RESOURCE_CONFLICT`

### Fall 4 – Abgelehnte Anfrage

* Status `REJECTED`
* Antwort mit `decision = REJECTED`
* `reasonCode = NO_CAPACITY`
* keine vertraulichen Daten über andere Projekte

## Snapshot-Inhalt

Der Snapshot soll einen plausiblen, aber reduzierten Takt-Ausschnitt enthalten.

Beispielsweise:

```json
{
  "schemaVersion": "1.0",
  "projectReference": "PROJECT-001",
  "taktReference": "TAKT-014",
  "taktVersion": 1,
  "trade": "DRYWALL",
  "workPackage": "Montage Trockenbauwände",
  "location": {
    "building": "Bauteil A",
    "storey": "EG",
    "zone": "Taktbereich 03"
  },
  "plannedTimeWindow": {
    "start": "2026-09-14T05:00:00Z",
    "end": "2026-09-18T14:00:00Z"
  }
}
```

Der Snapshot darf nicht enthalten:

* vollständigen Projektplan
* Takte anderer Nachunternehmer
* interne GU-Kommentare
* NU-Ressourcendaten

## Kompatibilität

* Bestehende Delegation-Seed-Daten bleiben erhalten.
* Bestehende Demo-Benutzer bleiben erhalten.
* Verwende vorhandene IDs beziehungsweise neue kollisionsfreie IDs.
* Seed muss mehrfach ausführbar sein, soweit die vorhandene Seed-Architektur dies unterstützt.

## Prüfungen

Führe aus:

* Datenbank-Reset oder Seed in Entwicklungsumgebung
* Typecheck
* Build
* vorhandene Seed-Tests

## Abschluss

Berichte:

* ergänzte Seed-Fälle
* erzeugte Taktanfragen
* erzeugte Antworten und Alternativen
* Ergebnis des Seeds
* weiterhin vorhandene bestehende Demo-Daten

* Beziehungen zu Takt, GU, NU und Benutzer
* Statusenum
* Indizes
* Unique Constraints

### Taktantwort

Prüfe:

* `takt_responses`
* `takt_response_alternatives`
* maximal eine Antwort pro Anfrage
* eindeutige Alternativen und Rangfolgen
* gültige Zeitfenster
* maximal drei Alternativen in der Service-Schicht

## Zustandsregeln

Prüfe:

* technische Zustellung ist keine fachliche Zustimmung
* `REJECTED` lehnt nicht automatisch den gesamten Takt ab
* `ALTERNATIVES_PROPOSED` bestätigt den Takt noch nicht
* `ACCEPTED` kann später den Takt bestätigen
* `SUPERSEDED` markiert eine ersetzte Anfrage
* terminale Zustände können nicht beliebig verändert werden

## Datenintegrität

Prüfe automatisiert oder durch Tests:

* Request referenziert existierenden Takt
* Request referenziert existierende Organisationen
* Snapshot ohne Request ist nicht möglich
* zweiter Snapshot für denselben Request wird abgelehnt
* zweite Response für denselben Request wird abgelehnt
* Alternative ohne Response ist nicht möglich
* doppelte `requestNumber` wird abgelehnt
* doppelte `messageId` wird abgelehnt, sofern gesetzt
* ungültiger Rang wird abgelehnt
* ungültige Zeitfenster werden abgelehnt

## Rückwärtskompatibilität

Bestätige:

* bestehende Delegation-Tabellen wurden nicht entfernt
* bestehende Delegation-Endpunkte wurden nicht entfernt
* bestehende GU-, NU- und Hub-Anwendungen bleiben startfähig
* bestehende Seed-Daten bleiben vorhanden
* bestehende Clients funktionieren weiterhin
* neue OpenAPI-Felder brechen bestehende Responses nicht
