REPLIT-AUFTRAG – VERBLEIBENDE FEHLER UND DOPPELIMPLEMENTIERUNGEN VOLLSTÄNDIG BEHEBEN

Arbeite im aktuellen Replit-Codebestand.

Replit ist die maßgebliche Arbeitsumgebung. Git dient der Veröffentlichung und externen Prüfung.

Prüfe vor jeder Änderung den tatsächlich vorhandenen Code. Wenn ein hier genannter Service, Helper oder Dateiname inzwischen anders heißt oder bereits teilweise refaktoriert wurde, KEINE parallele Implementierung anlegen, sondern die vorhandene aktuelle Struktur entsprechend vervollständigen.

Dieser Auftrag ist eine Fehlerbereinigung und Konsolidierung. Keine neuen fachlichen Features implementieren.

A. TERMINÄNDERUNGEN / CHANGE PROPOSALS
============================================================

A1. EINE EINZIGE ZENTRALE SCHEDULE-CHANGE-LOGIK

Suche nach den aktuell vorhandenen Funktionen/Services für:

- applyAcceptedScheduleChange
- service-change-proposal-service
- schedule-change-service

Eine akzeptierte Terminänderung darf fachlich nur über EINEN zentralen Schedule-Change-Service angewendet werden.

Der Change-Proposal-Service darf NICHT zusätzlich selbst unabhängig ändern:

- agreedStart
- agreedEnd
- plannedStart
- plannedEnd
- Resource Requirements
- Resource Bookings
- Planversion

Zielstruktur sinngemäß:

async function acceptChangeProposal(...) {
  return db.transaction(async (tx) => {
    // Proposal exklusiv/konkurrenzsicher laden
    // OPEN prüfen
    // Service Request + Agreement laden
    // Schedule Change vorbereiten
    // Availability prüfen
    // Schedule Change vollständig anwenden
    // Proposal ACCEPTED setzen
    // Commit
  });
}

Bestehende Lock-/Concurrency-Lösung weiterverwenden.


------------------------------------------------------------
A2. DOUBLE SHIFT BEI WIEDERHOLTEN TERMINÄNDERUNGEN BESEITIGEN
------------------------------------------------------------

Problem:

Nach einer ersten akzeptierten Terminänderung können Resource Requirements bereits verschoben gespeichert sein.

Beispiel:

ursprünglich:
Agreement 01.–05.09.
Requirement 02.–03.09.

nach erster Änderung:
Agreement 06.–10.09.
Requirement 07.–08.09.

zweite Änderung:
Agreement 11.–15.09.

Dann muss Requirement werden:
12.–13.09.

Es darf NICHT erneut relativ zum ursprünglichen 01.09. verschoben werden.

Vereinheitliche den vorhandenen Requirement-Shift-Helper auf exakt diese Semantik:

function shiftRequirementsToWindow(
  requirements,
  currentAgreementStart,
  targetAgreementStart
)

Berechnung:

const shiftDays = differenceInCalendarDays(
  targetAgreementStart,
  currentAgreementStart
);

Dann je Requirement:

shifted.periodStart =
  shiftCalendarDate(requirement.periodStart, shiftDays);

shifted.periodEnd =
  shiftCalendarDate(requirement.periodEnd, shiftDays);

Keine Berechnung gegen den ursprünglichen Snapshot.

Keine Millisekundenarithmetik.

A3. SHIFTED REQUIREMENTS GENAU EINMAL BERECHNEN
------------------------------------------------------------

Nicht zulässig:

Availability Service berechnet shiftedRequirements A
und
Schedule Change Service berechnet später unabhängig shiftedRequirements B.

Stattdessen exakt einmal:

const shiftedRequirements = shiftRequirementsToWindow(
  requirements,
  currentAgreementStart,
  proposal.start
);

Genau dieses Array verwenden für:

- Availability Check
- Requirement Update
- Booking Generation

Verbindliche Regel:

Der Zeitraum, für den Availability geprüft wird, muss exakt dem Zeitraum entsprechen, der anschließend gespeichert und gebucht wird.

------------------------------------------------------------
A7. EXAKTE TRANSAKTIONSREIHENFOLGE
------------------------------------------------------------

Innerhalb EINER DB-Transaktion:

1. Proposal laden / sperren
2. status == OPEN prüfen
3. Service Request laden
4. Current Agreement prüfen
5. aktuelle Resource Requirements laden
6. request-eigene Bookings laden
7. Calendar-Date-Validation
8. shiftedRequirements erzeugen
9. Availability prüfen
10. bei Conflict THROW → Rollback
11. neue Leistungsversion erzeugen
12. aktiven Plan aktualisieren
13. Agreement aktualisieren
14. ResourceRequirement-Zeiträume aktualisieren
15. request-eigene Bookings aktualisieren/ersetzen
16. Proposal auf ACCEPTED setzen
17. Commit

Keine fachliche Mutation außerhalb dieser Transaktion.

→ HTTP 409 CHANGE_PROPOSAL_NOT_FEASIBLE

F4. GREEDY / CONSERVATIVE ALLOCATION
------------------------------------------------------------

2. nur Resources mit remainingCapacity > 0
3. benötigte effektive Kapazität:

  requiredCapacity * utilizationPercent / 100;

→ CONFLICT

============================================================
AM. DEFINITION OF DONE
============================================================

Der Auftrag gilt erst als abgeschlossen, wenn ALLE folgenden Aussagen stimmen:

1. Eine zweite Terminänderung erzeugt keinen Double Shift.

2. Availability und spätere Buchung verwenden exakt dieselben shifted Requirements.

3. Eine nicht verfügbare Terminänderung führt zu 409 und vollständigem Rollback.

4. Agreement, Plan, Version, Requirements und Bookings sind nach Accept konsistent.

5. Konkrete Resource-Zuordnungen bleiben erhalten, wenn die Resource im neuen Zeitraum verfügbar ist.

6. Legacy Requests ohne ResourceRequirements verlieren ihre Bookings nicht.

7. Initial Acceptance und Change Acceptance verwenden dieselbe Booking-Erzeugungslogik.

8. Auto-Booking verwendet bookingRequirements.

9. Unterschiedliche Requirement-Zeiträume werden nicht zusammengezogen.
