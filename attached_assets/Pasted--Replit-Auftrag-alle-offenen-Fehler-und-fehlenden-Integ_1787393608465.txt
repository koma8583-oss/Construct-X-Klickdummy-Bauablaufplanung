# Replit-Auftrag – alle offenen Fehler und fehlenden Integrationen beheben

Arbeite im aktuellen Repository-Stand.

Ziel: **Nur die aktuell offenen Fehler, Inkonsistenzen und nicht vollständig integrierten Funktionen beheben.** Keine neuen Features darüber hinaus.

Wichtig:

* keine große Refaktorierung
* keine neue Architektur
* keine Workflow-Engine
* kein Event Sourcing
* keine neue EDC-Integration
* technische Bezeichner im Code Englisch
* UI-Texte Deutsch
* bestehende Datenmodelle möglichst weiterverwenden
* bestehende zentrale Services wiederverwenden
* keine doppelte Fachlogik erzeugen
* vorhandene Legacy-`takt...`-Bezeichner nur dort belassen, wo eine Migration unnötig wäre

# A. P0 – fachliche Kernfehler zuerst beheben

## 1. Accepted Change Proposal muss den tatsächlichen Plan vollständig aktualisieren

Prüfe insbesondere:

```text
artifacts/api-server/src/services/service-change-proposal-service.ts
artifacts/api-server/src/services/gu-decision-service.ts
```

Aktuelles Problem:

Bei `ACCEPTED` werden nur:

```text
agreedStart
agreedEnd
```

aktualisiert.

Der eigentliche Plan und die Ressourcenbelegung bleiben auf dem alten Zeitraum.

Das ist fachlich nicht zulässig.

## Ziel

Eine akzeptierte Terminänderung muss atomar den gesamten vereinbarten Zustand aktualisieren.

Erstelle dafür einen zentralen Service/Helper:

```text
applyAcceptedScheduleChange(...)
```

z. B. in:

```text
artifacts/api-server/src/services/schedule-change-service.ts
```

Nicht dieselbe Logik erneut direkt im Change-Proposal-Service implementieren.

---

## 1.1 Eingaben

Mindestens:

```ts
{
  serviceRequestId: string;
  newStart: string;
  newEnd: string;
  initiatedBy: "AG" | "AN";
  proposalId?: string;
}
```

---

## 1.2 Ablauf

Innerhalb einer DB-Transaktion:

```text
1. Service Request laden
2. aktuelle Vereinbarung laden
3. neue Datumswerte validieren
4. Resource Requirements laden
5. neue Requirement-Zeiträume bestimmen
6. AN-Verfügbarkeit für neuen Zeitraum prüfen
7. falls nicht machbar → Abbruch, keine Änderung
8. eigentlichen Plan/Leistung aktualisieren
9. Plan-/Leistungsversion erhöhen, falls dieses Modell vorhanden ist
10. agreedStart/agreedEnd aktualisieren
11. bestehende automatisch erzeugte CONFIRMED ResourceBookings aktualisieren
12. Proposal auf ACCEPTED setzen
```

Keine Teiländerungen.

---

## 1.3 Requirement-Zeiträume verschieben

Wenn ein Requirement einen Teilzeitraum besitzt:

Beispiel:

```text
alte Vereinbarung:
01.–20.09.

Requirement:
10.–12.09.
```

Offset:

```text
+9 bis +11 Tage
```

Neue Vereinbarung:

```text
15.–34.09. sinngemäß
```

Requirement muss entsprechend relativ verschoben werden.

Vorhandenen Helper zur Verschiebung von Requirements wiederverwenden.

Keine zweite Offset-Logik schreiben.

---

## 1.4 ResourceBookings aktualisieren

Nur Bookings, die fachlich aus diesem Service Request stammen, ändern.

Erkennbar z. B. über:

```text
sourceType = SERVICE_REQUEST / TAKT_REQUEST
sourceReferenceId = serviceRequestId
```

oder bestehende passende Felder.

Nicht manuelle oder andere Projektbuchungen verändern.

Für Type-Level-Bookings:

```text
resourceId = null
resourceTypeId bleibt
quantity bleibt
utilizationPercent bleibt
```

Nur Zeitraum verschieben.

Für konkrete ResourceBookings:

* Resource-Zuordnung beibehalten
* Zeitraum verschieben
* vorher Verfügbarkeit prüfen

# 2. Availability-Berechnung auf tagesweise Kapazität umstellen

Prüfe:

```text
resource-availability-service.ts
```

Aktuell werden alle Bookings, die den Requirement-Zeitraum irgendwo überlappen, summiert.

Das ist falsch.

## Ziel

Kapazität pro Kalendertag berechnen.

Für jeden Requirement-Tag:

```text
confirmedUsed(day)
tentativeUsed(day)
required(day)
```

berechnen.

---

## 2.1 Pro Tag

Für konkrete ResourceBooking:

```text
used =
resource.capacity
* booking.utilizationPercent / 100
```

Für Type-Level-Booking:

```text
used =
booking.quantity
* booking.utilizationPercent / 100
```

Nur wenn das Booking den konkreten Tag umfasst.

---

## 2.2 Verfügbarkeit

Pro Tag:

```text
availableConfirmed =
totalCapacity - confirmedUsed
```

```text
projectedAvailable =
totalCapacity - confirmedUsed - tentativeUsed
```

---

## 2.3 Requirement machbar

Requirement ist nur `FEASIBLE`, wenn an **jedem relevanten Tag**:

```text
availableConfirmed >= effectiveRequired
```

mit:

```text
effectiveRequired =
requiredCapacity * utilizationPercent / 100
```

---

## 2.4 Ergebnis erweitern

Falls möglich, Ergebnis zusätzlich mitgeben:

```ts
dailyAvailability?: Array<{
  date: string;
  totalCapacity: number;
  confirmedUsed: number;
  tentativeUsed: number;
  requiredCapacity: number;
  availableCapacity: number;
}>
```

Diese Daten später für UI-Konflikttage wiederverwenden.

# 3. Gleichzeitige Requirements desselben ResourceType aggregieren

Im selben Evaluator korrigieren.

Aktuell werden Requirements einzeln geprüft.

## Ziel

Für jeden:

```text
resourceTypeId + day
```

alle gleichzeitig geltenden Requirements aggregieren.

Beispiel:

```text
Requirement A = 4 Personen
Requirement B = 3 Personen
Gesamtkapazität = 6
```

Ergebnis:

```text
7 > 6
→ Konflikt
```

---

## Umsetzung

Vor Availability-Prüfung intern eine Tagesstruktur erzeugen:

```ts
Map<resourceTypeId, Map<date, effectiveRequiredCapacity>>
```

Alle Requirements desselben Types auf demselben Tag addieren.

Qualifikationsspezifische Requirements nicht blind zusammenfassen, wenn sie unterschiedliche `requiredQualification` besitzen.

Für den PoC:

```text
resourceTypeId + requiredQualification + day
```

als Gruppierung verwenden.



# 40. Invalid Decision niemals zu ACCEPTED mappen

In:

```text
external-mappers.ts
```

nur erlauben:

```text
ACCEPTED
REJECTED
ALTERNATIVES_PROPOSED
```

Alles andere:

```text
throw InvalidExternalServiceResponse
```

Kein Default auf `ACCEPTED`.

# 41. `messageId` aus bestehendem Envelope übernehmen

Mapper so erweitern, dass optional:

```text
messageId
```

mitgegeben werden kann.

Bei Mapping aus bestehendem Envelope:

```text
external.metadata.messageId = envelope.messageId
```

Nicht immer neue UUID erzeugen.

Neue UUID nur, wenn keine Message-ID vorhanden ist.

# 43. Inbound-Service wirklich verdrahten

Produktiver Empfang von:

```text
ExternalServiceRequest
ExternalServiceResponse
```

muss über:

```ts
handleIncomingServiceRequest(...)
handleIncomingServiceResponse(...)
```

laufen.

Damit aktivieren:

```text
Inbound Audit
Idempotenz
RECEIVED
PROCESSED
FAILED
```
